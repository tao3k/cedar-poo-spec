#+TITLE: Protected Storage V1
#+OPTIONS: toc:nil

[[file:ProtectedStorage.lean][ProtectedStorage V1]] separates intent admission
from publication commit. =ProtectionIntentV1= binds the inner snapshot CID,
complete source labels, destination, subject, purpose, policy root, lineage,
storage tier, protection profile, key reference, key version and residency.
The key reference is an identity, never secret material. The Host authenticates the
source catalog, destination configuration and current policy before any
encryption or provider I/O.

After encryption, =ProtectedPublicationV1= binds the intent to a distinct outer
root CID and envelope version, and requires the actual key version to equal
the authorized intent. =preRootAdmitted= rechecks the claim and current
policy, lineage, epoch and expiry immediately before the outer-root PUT. A
restricted source may enter only a destination that explicitly accepts it;
protection does not declassify that source.

=commitDisposition= then projects a separate Host ledger decision. A fresh
commit requires a physical root acknowledgement for the exact inner and outer
roots, positive outer bytes, bounded child count, and current authority. An
authenticated existing receipt for the exact publication yields =replay= even
if authority later expires; it creates no new effect and grants no read access.
A conflicting receipt or missing acknowledgement yields =reject=. The Host
owns atomic compare-and-set of the operation ledger, discoverability pointer,
approval redemption, and audit.

The Host must verify the actual encrypted envelope and complete inner and
outer snapshot closures, bind the outer root to the exact authorized intent,
redeem the operation ID once, and atomically persist its result and audit.
These pure Lean checks cannot establish encryption, authenticate a claim,
control concurrent state, or commit a durable effect. A failed publication may
leave undiscoverable ciphertext that the Host later collects.

[[file:../../Productions/Data/ProtectedStorageFixture.lean][The fixture]] exports
fourteen intent, nine pre-root, and fourteen commit disposition cases to
[[file:../../Tests/Conformance/protected-storage-v1.json][checked JSON]].
[[file:../../Tests/Data/ProtectedStorage.lean][Lean tests]] fix two accepted
intents, one accepted publication, and apply/replay/reject outcomes. Rust
consumers replay the same fixture. [[file:ProtectionProfile.lean][ProtectionProfile]]
uses LeanPoo object slots and inheritance to recompute an intent after a
profile override; [[file:../../Tests/Data/ProtectionProfile.lean][tests]] retain
the parent version and source custody. The
[[file:../../docs/reflection/protected-storage-commit.org][iteration Reflection]]
records the LeanPoo capability choice and its executable evidence.

[[file:ProtectedRead.lean][Protected Read V1]] requires an authenticated exact
commit receipt plus a fresh, action-specific read claim for the reader,
purpose, destination, policy root, lineage, epoch and expiry. It checks all
retained source labels against that reader. A write approval or commit replay
does not authorize a read; neither does possession of a key or a warm cache.
The same checked JSON now includes fifteen read cases (two allow, thirteen
deny). The [[file:../../docs/reflection/protected-storage-read.org][read
Reflection]] records the LeanPoo assessment for this slice.
