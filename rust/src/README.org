* Cargo features

| Feature | Provides | Heavy dependency |
|---------+----------+------------------|
| =cedar-runtime= | Official Cedar validation and replay | =cedar-policy= |
| =agentic-ai-boundary= | Typed tool-action and sink checks, including observable selection mutations | None |
| =agentic-ai-language-model-disclosure-host= | In-memory reference Host for tool-using language-model disclosure | =cedar-runtime= |
| =pseudonymization= | Borrowed common token mode and lineage profile | None |
| =google-sdp= | Google table request and response contract | =base64= and =sha2= |
| =google-sdp-host= | In-memory Cedar-to-Google admission example API | Both features above |
| =mandate-offer-signatures= | Public mandate, delegation, and offer signature verifier API | =p256= and =sha2= |
| =lean-mandate-offer-projection= | Exact mandate and offer claims comparison for Lean admission | =mandate-offer-signatures= |
| =agent-commerce-admission= | Process-local admission checks for signed root, child chain, and offer claims | =lean-mandate-offer-projection= |

The common =pseudonymization= profile compiles without =cedar-policy= or a
cloud SDK. =google-sdp= adds the Google wire contract and includes that common
profile; it also compiles without =cedar-policy=. The in-memory Google
admission boundary needs =google-sdp-host=. The language-model disclosure Host is
opt-in, so enabling generic Cedar replay does not compile its reference API.
The =agentic-ai-boundary= feature is independent of Cedar runtime and mirrors
the [[file:../../CedarPooSpec/AgenticAI/Boundary.lean][Lean multimethod
contract]]. The Host feature includes it and supplies the official Cedar
reauthorization and process-local ledger.

The mandate and offer verifier is compiled from [[file:mandate_offer_signatures.rs][=rust/src/mandate_offer_signatures.rs=]]
and exported by the library only with =mandate-offer-signatures=. Downstream Rust
consumers can depend on =cedar-poo-bridge= with =default-features=false= and
=features=["mandate-offer-signatures"]=. The [[file:../tests/integration/mandate_offer_signatures_consumer.rs][external consumer test]] calls its
public signing-byte and verification API through the crate boundary. No
Agent Commerce implementation is supplied from =rust/examples=; the Lean
scenario under =Examples/= provides only synthetic inputs. The feature uses
neither =cedar-runtime= nor =cedar-policy=. Its name reflects the exact
research slice: signatures on a principal mandate, each narrower agent
delegation, and a merchant offer, plus a hash of checkout bytes. Verified
delegation values retain ancestor identities and reject their reuse on later
hops. It does not verify an agent's HTTP request identity, evaluate an AP2
mandate chain, issue
a credential, allocate a durable budget, dispatch to a provider, manage
issuer keys, or provide the checked Lean mapping.

The separate [[file:lean_mandate_offer_projection.rs][Lean projection API]] accepts live =VerifiedMandate= and =VerifiedOffer=
values and compares every signed field to typed Lean claims. It excludes the
Host-owned =verified= flags and rejects unknown JSON fields. The
[[file:../tests/integration/lean_mandate_offer_projection_consumer.rs][consumer test]] compares Rust's verified objects to JSON emitted by the public
Lean types through =just check-agent-commerce-projection=. The Host must keep
the verified values in its trusted process and set =verified= only after the
comparison and its separate current-time, key-status, policy, and revocation
checks. JSON claims alone do not carry cryptographic authority.

The separate [[file:agent_commerce_admission.rs][Agent Commerce admission reference]] re-verifies a principal-signed root mandate,
each parent-agent-signed child mandate, and a merchant offer against current
keys and exact checkout bytes on every call. It rejects inactive issuer keys,
expired evidence, missing or stale policy epochs, revoked mandate or offer
IDs, revoked Agent keys, changed Lean lineage or offer claims, and offers
outside the final mandate scope. The Host passes a trusted clock reading and
a policy evaluator over the exact claims. These inputs and registry changes
must be authenticated by a deployment. The returned claims contain no reusable
=verified= flag; a reservation or external effect needs a fresh state check.
This process-local API does not authenticate Agent request possession, persist
revocations or a shared budget, or run Cedar itself.
The [[file:../tests/integration/agent_commerce_admission_consumer.rs][external consumer test]] exercises these dynamic refusals under
=agent-commerce-admission=.

* Google table transformation contract

[[file:google_sdp.rs][google_sdp.rs]] maps the selected Lean table input to the official Google
Sensitive Data Protection =projects.locations.content.deidentify= and
=reidentify= REST body shapes. It selects one entire table column through
=RecordTransformations.FieldTransformation=, takes the context from a second
column, and uses a Host-resolved KMS-wrapped data key. The same transformation
configuration is used in the reverse request. The [[file:../../CedarPooSpec/Pseudonymization/README.org][public Lean capability]]
owns the generic recipe; the [[file:../../Examples/Health/Pseudonymization/README.org][hospital example]] supplies a synthetic selected row.

The =SelectedTabularInput= and =WrappedKeyBinding= must agree on key domain,
token-key version, and wrapping version before a request is constructed. The
Host must authenticate both inputs and resolve the actual key. This check
does not prove that the wrapped bytes contain that version of the data key.

The caller supplies a provider response through an authenticated transport.
=check_deidentify_response= and =check_reidentify_response= require the
expected table shape, unchanged context, one reported successful field
transformation, and the expected transformation or recovery of the selected
cell. De-identification also checks the Base64 AES-SIV token and any declared
surrogate name and encoded length. Their output binds hashes of the request
and response JSON. An
arbitrary JSON document can satisfy the shape check; it is not itself proof
of Google execution, a persisted audit, or atomic Host admission.
The [[file:../examples/pseudonymization_google_contract.rs][offline example runner]] consumes two explicitly synthetic provider-shape
responses from the hospital scenario and emits request/response digests.
The [[file:google_sdp_host.rs][in-memory admission API]] replays a schema-validated Cedar case,
binds the selected row, Google endpoint, and exact request body, and releases a caller-supplied
response only after a digest audit entry is appended. The
[[file:../examples/pseudonymization_google_admission.rs][hospital consumer]] owns synthetic responses in its scenario directory.
The in-memory Host records a digest of each admitted token with its dataset,
tenant, context, token-key version, and transformation revision. Recovery requires
that lineage; a token with no prior admitted issuance is rejected. This
registry is process-local evidence and does not authenticate a Google response
or replace a durable token catalog in a deployed Host.
The API has no embedded fixture. Its audit and approval revision live only in
process memory, so this does not establish durable or provider-authenticated
execution.

[[https://docs.cloud.google.com/sensitive-data-protection/docs/reference/rest/v2/projects.locations.content/deidentify][Google de-identify REST method]],
[[https://docs.cloud.google.com/sensitive-data-protection/docs/reference/rest/v2/projects.locations.content/reidentify][Google re-identify REST method]], and
[[https://docs.cloud.google.com/sensitive-data-protection/docs/reference/rest/v2/projects.deidentifyTemplates#CryptoDeterministicConfig][CryptoDeterministicConfig reference]] define the wire format.

* Approval-instance consumption

[[file:authority_consumption.rs][AuthorityLedger]] is a small Rust counterpart of the public
[[file:../../CedarPooSpec/Admission/AuthorityConsumption.lean][Lean admission model]]. It matches one stable ID to one exact effect and
rejects missing, duplicate, mismatched, and exhausted grants. The
[[file:agentic_ai/language_model/disclosure_host.rs][in-memory disclosure Host]] rechecks Cedar and consumes an approval
under the same lock as its budget, cohort, and audit update. The
[[file:../examples/agentic_ai_language_model_disclosure_host.rs][offline consumer]] exercises fresh-ticket replay, concurrent tickets,
separate approvals, and failure before consumption.

[[file:operation_identity.rs][OperationLedger]] binds a logical operation ID to its exact effect.
The Host checks it at preparation and commits it alongside approval use and
budget debit. The offline consumer rejects a fresh approval for the same
operation while allowing an independent operation with identical payload.

This lock gives process-local serialization only. A downstream Host must
authenticate the approval store and implement the same mutation in durable
transactional storage. It also needs an idempotent external-effect protocol:
the in-memory receipt does not prove delivery or resolve an uncertain sink
response after a crash.

* Local cryptographic check

[[file:../examples/pseudonymization_local.rs][pseudonymization_local.rs]] uses RustCrypto with a synthetic key to check
deterministic encryption, context separation, and local reversal after
governed Cedar decisions. Google internally expands its supplied key and
specifies its own context handling. The local RustCrypto output is therefore
not asserted to be byte-for-byte interchangeable with a Google token. The
Google request and response boundary above is kept separate from this local
check.
