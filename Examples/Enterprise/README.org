* Source and model boundary

[[file:PurchaseApproval.lean][PurchaseApproval.lean]] combines two published
mechanisms in a fictive procurement model. Cedar documents
[[https://docs.cedarpolicy.com/policies/syntax-operators.html][decimal comparison
operators]] including =lessThanOrEqual=, which the model uses for a request
amount and an order-specific limit. This example additionally requires the
requested amount to be strictly positive. [[https://csrc.nist.gov/CSRC/media/Projects/risk-management/800-53%20Downloads/800-53r5/SP_800-53_v5_1-derived-OSCAL.pdf][NIST SP 800-53 AC-5]]
describes separation of duties as a security control; the model represents
one narrow instance by forbidding a requester to approve their own order.
Neither source prescribes this example's amount, department structure, or
policy module layout. The =500.0000= limit and every identity are fictive.

The application must establish the order requester, order group, approval
amount, and authenticated principal before calling Cedar. The model proves
neither the provenance of those facts nor completion of a purchase.

* Delegation source and application assumptions

[[https://docs.cedarpolicy.com/bestpractices/bp-using-the-context.html][Cedar's context guidance]] explicitly describes the pattern where a user
remains the principal and an agent appears in =context.viaAgent=. It also
requires the application to include both entities in the entity store.
[[file:DelegatedApproval.lean][DelegatedApproval.lean]] uses that pattern for
procurement. The bot's operator binding, enabled flag, and explicit
revocation are modeled requirements, not claims from Cedar or NIST. The
caller must authenticate the agent and populate its entity facts; Cedar
does not authenticate these inputs.

* POO evolution

=Base= permits operations approvers and deliberately lacks an amount bound.
=Budget= overlays that policy with a decimal comparison against the order's
limit. =Duties= independently adds a self-approval forbid. =Integrated=
composes both branches. =Delegated= overlays the bounded permit with
an agent operator and enabled check while preserving the duties veto.
=Revoked= extends that root with a forbid for the purchasing bot. The
nine original named requests expose what each branch
alone misses: a self-approval below the limit and another approver's request
above it. They also check the exact limit, one unit in the fourth decimal
place above and below it, zero and negative amounts, and a cross-department
request.

The ten [[file:DelegatedApprovalExport.lean][delegation requests]] distinguish
an active agent, self approval, amount over the limit, inactive agent,
missing agent, wrong department, zero and negative amounts, and revoked
agent. An attribute-presence check makes a missing agent a clean deny rather
than a policy evaluation error. The
[[file:DelegatedApprovalMatrixExport.lean][160-request matrix]] crosses both
final roots with two users, two orders, four agent identities, and five
amounts. It asserts an independent expected decision for each combination,
requires no Lean policy evaluation errors, and compares every receipt with
the official Cedar Rust authorizer.

=delegatedPublication= and
=revokedPublication= establish schema and Cedar policy validation before
publication. [[file:PublishedPolicy.lean][PublishedPolicy.lean]] emits the
validated JSON; the check compares that exact JSON to the delegated
conformance receipt, then the Rust bridge checks it and the generated
[[file:DelegatedPolicies/delegated.cedar][Cedar source]]. These are finite
conformance examples, not proofs that an arbitrary caller supplies genuine
identity, delegation, or revocation state.

=budgetEditLocal= checks that the budget revision changes only the permit
body. =decisionsExactFully= checks the finite Lean request table. The
[[file:PurchaseApprovalExport.lean][exporter]] feeds those same requests to
the official Rust Cedar authorizer and reparses the generated
[[file:Policies/integrated.cedar][integrated policy source]]. This checks the
translation boundary for these requests; it is not a general procurement
compliance certification.

The generated =.cedar= files contain only the surviving materialized
policies. C4 parent order, overlay history, and removed or replaced bodies
are resolved in Lean before export. A short Cedar file therefore reflects
the small policy model, while the Lean modules record its evolution. The
checks establish behavior for these inputs; they do not establish genuine
agent authentication, grant provenance, or complete enterprise coverage.

* Compound payment release

[[file:PaymentRelease.lean][PaymentRelease.lean]] models a payment release that
requires two Cedar queries on the same payment snapshot: the recorded clerk
may prepare it, and a different controller may release it. The application
combines both =Allow=
results before performing the payment. This follows Cedar's
[[https://docs.cedarpolicy.com/bestpractices/bp-compound-auth.html][compound authorization guidance]] for activities involving multiple
parties. The [[https://www.gao.gov/greenbook][GAO Green Book]] describes internal controls over improper
payments, and [[https://csrc.nist.gov/CSRC/media/Projects/risk-management/800-53%20Downloads/800-53r5/SP_800-53_v5_1-derived-OSCAL.pdf][NIST AC-5]] describes separation of duties. Neither source
prescribes the fictional roles, payment states, or =500.0000= threshold in
this example. [[file:../../CedarPooSpec/CompoundAuthorization.lean][CompoundAuthorization.authorizeAll]] compiles one POO root
once, evaluates both requests against the same supplied entity store, and
retains their exact responses. Its =allowed= projection rejects an empty
request list and any policy evaluation error.

The POO roots keep independent control changes visible:

| Root | Payment release change |
|------+------------------------|
| =Base= | A legacy matched-payment permit allows any user to release. |
| =Threshold= | A controller permit adds a senior role requirement above =500.0000=. |
| =Duties= | A preparer cannot release the same payment. |
| =Risk= | A blocked payment cannot be released. |
| =Retired= | The legacy broad release permit is removed. |
| =Integrated= | All four changes compose; four policies survive. |

=controlsNeedCompositionFully= proves why a partial update is insufficient:
the legacy permit bypasses =Threshold=, while =Retired= alone leaves the
ordinary controller permit unbounded. The final root denies both paths.
=thresholdEditLocal= identifies the one overlaid policy, and =legacyRetired=
checks the surviving policy IDs. The [[file:PaymentReleaseExport.lean][exporter]]
checks both authorization requests for each of ten operations, plus eight
branch probes, against the official Rust Cedar authorizer. The
[[file:PublishedPayment.lean][publication entrypoint]] emits the integrated
JSON only after schema and policy validation; its JSON and generated
[[file:PaymentPolicies/integrated.cedar][Cedar source]] are compared with the
conformance artifact.

The entity store supplies =preparedBy=, =matched=, =blocked=, and the payment
amount. An application must authenticate the two actors, obtain those facts
from an authoritative workflow, bind both queries to one consistent payment
snapshot, enforce the conjunction, and execute the transfer transactionally.
The Lean example computes the authorization conjunction; it does not
implement a payment workflow or prove that those external facts are genuine.
The wrong-preparer case checks that the first query cannot be performed by a
clerk other than the payment's recorded =preparedBy=.
