* Source and model boundary

[[file:PurchaseApproval.lean][PurchaseApproval.lean]] combines two published
mechanisms in a fictive procurement model. Cedar documents
[[https://docs.cedarpolicy.com/policies/syntax-operators.html][decimal comparison
operators]] including =lessThanOrEqual=, which the model uses for a request
amount and an order-specific limit. This example additionally requires the
requested amount to be strictly positive. [[https://csrc.nist.gov/CSRC/media/Projects/risk-management/800-53%20Downloads/800-53r5/SP_800-53_v5_1-derived-OSCAL.pdf][NIST SP 800-53 AC-5]]
describes separation of duties as a security control; the model represents
one narrow instance by forbidding a requester to approve their own order.
Neither source prescribes this example's amount, department structure, or
policy module layout. The =500.0000= limit and every identity are fictive.

The application must establish the order requester, order group, approval
amount, and authenticated principal before calling Cedar. The model proves
neither the provenance of those facts nor completion of a purchase.

* Delegation source and application assumptions

[[https://docs.cedarpolicy.com/bestpractices/bp-using-the-context.html][Cedar's context guidance]] explicitly describes the pattern where a user
remains the principal and an agent appears in =context.viaAgent=. It also
requires the application to include both entities in the entity store.
[[file:DelegatedApproval.lean][DelegatedApproval.lean]] uses that pattern for
procurement. The bot's operator binding, enabled flag, and explicit
revocation are modeled requirements, not claims from Cedar or NIST. The
caller must authenticate the agent and populate its entity facts; Cedar
does not authenticate these inputs.

* POO evolution

=Base= permits operations approvers and deliberately lacks an amount bound.
=Budget= overlays that policy with a decimal comparison against the order's
limit. =Duties= independently adds a self-approval forbid. =Integrated=
composes both branches. =Delegated= overlays the bounded permit with
an agent operator and enabled check while preserving the duties veto.
=Revoked= extends that root with a forbid for the purchasing bot. The
nine original named requests expose what each branch
alone misses: a self-approval below the limit and another approver's request
above it. They also check the exact limit, one unit in the fourth decimal
place above and below it, zero and negative amounts, and a cross-department
request.

The ten [[file:DelegatedApprovalExport.lean][delegation requests]] distinguish
an active agent, self approval, amount over the limit, inactive agent,
missing agent, wrong department, zero and negative amounts, and revoked
agent. An attribute-presence check makes a missing agent a clean deny rather
than a policy evaluation error. The
[[file:DelegatedApprovalMatrixExport.lean][160-request matrix]] crosses both
final roots with two users, two orders, four agent identities, and five
amounts. It asserts an independent expected decision for each combination,
requires no Lean policy evaluation errors, and compares every receipt with
the official Cedar Rust authorizer.

=delegatedPublication= and
=revokedPublication= establish schema and Cedar policy validation before
publication. [[file:PublishedPolicy.lean][PublishedPolicy.lean]] emits the
validated JSON; the check compares that exact JSON to the delegated
conformance receipt, then the Rust bridge checks it and the generated
[[file:DelegatedPolicies/delegated.cedar][Cedar source]]. These are finite
conformance examples, not proofs that an arbitrary caller supplies genuine
identity, delegation, or revocation state.

=budgetEditLocal= checks that the budget revision changes only the permit
body. =decisionsExactFully= checks the finite Lean request table. The
[[file:PurchaseApprovalExport.lean][exporter]] feeds those same requests to
the official Rust Cedar authorizer and reparses the generated
[[file:Policies/integrated.cedar][integrated policy source]]. This checks the
translation boundary for these requests; it is not a general procurement
compliance certification.

The generated =.cedar= files contain only the surviving materialized
policies. C4 parent order, overlay history, and removed or replaced bodies
are resolved in Lean before export. A short Cedar file therefore reflects
the small policy model, while the Lean modules record its evolution. The
checks establish behavior for these inputs; they do not establish genuine
agent authentication, grant provenance, or complete enterprise coverage.

* Compound payment release

[[file:PaymentRelease.lean][PaymentRelease.lean]] models a payment release that
requires two Cedar queries on the same payment snapshot: the recorded clerk
may prepare it, and a different controller may release it. The application
combines both =Allow=
results before performing the payment. This follows Cedar's
[[https://docs.cedarpolicy.com/bestpractices/bp-compound-auth.html][compound authorization guidance]] for activities involving multiple
parties. The [[https://www.gao.gov/greenbook][GAO Green Book]] describes internal controls over improper
payments, and [[https://csrc.nist.gov/CSRC/media/Projects/risk-management/800-53%20Downloads/800-53r5/SP_800-53_v5_1-derived-OSCAL.pdf][NIST AC-5]] describes separation of duties. Neither source
prescribes the fictional roles, payment states, or =500.0000= threshold in
this example. [[file:../../CedarPooSpec/CompoundAuthorization.lean][CompoundAuthorization.authorizeAll]] compiles one POO root
once, evaluates both requests against the same supplied entity store, and
retains their exact responses. Its =allowed= projection rejects an empty
request list and any policy evaluation error.

The POO roots keep independent control changes visible:

| Root | Payment release change |
|------+------------------------|
| =Base= | A legacy matched-payment permit allows any user to release. |
| =Threshold= | A controller permit adds a senior role requirement above =500.0000=. |
| =Duties= | A preparer cannot release the same payment. |
| =Risk= | A blocked payment cannot be released. |
| =Retired= | The legacy broad release permit is removed. |
| =Integrated= | All four changes compose; four policies survive. |

=controlsNeedCompositionFully= proves why a partial update is insufficient:
the legacy permit bypasses =Threshold=, while =Retired= alone leaves the
ordinary controller permit unbounded. The final root denies both paths.
=thresholdEditLocal= identifies the one overlaid policy, and =legacyRetired=
checks the surviving policy IDs. The [[file:PaymentReleaseExport.lean][exporter]]
checks both authorization requests for each of ten operations, plus eight
branch probes, against the official Rust Cedar authorizer. The
[[file:PublishedPayment.lean][publication entrypoint]] emits the integrated
JSON only after schema and policy validation; its JSON and generated
[[file:PaymentPolicies/integrated.cedar][Cedar source]] are compared with the
conformance artifact.

The entity store supplies =preparedBy=, =matched=, =blocked=, and the payment
amount. An application must authenticate the two actors, obtain those facts
from an authoritative workflow, bind both queries to one consistent payment
snapshot, enforce the conjunction, and execute the transfer transactionally.
The Lean example computes the authorization conjunction; it does not
implement a payment workflow or prove that those external facts are genuine.
The wrong-preparer case checks that the first query cannot be performed by a
clerk other than the payment's recorded =preparedBy=.

* AI agent delegation across three authorization layers

[[file:AgentDelegation.lean][AgentDelegation.lean]] adapts the three checks in
[[https://github.com/aws-samples/sample-cedar-agentic-ai-authorization][AWS's published Cedar agent delegation sample]]: agent-to-tool,
agent-to-agent delegation, and originating-user authorization. The sample
notes that agent attributes and user claims need an authoritative source.
This example keeps agent attributes in Cedar entities and takes the original
user as a context entity reference; it does not implement the sample's HMAC
or OAuth token exchange.

| Evidence | Local contract |
|----------+----------------|
| [[https://arxiv.org/abs/2606.28679][ScopeGate preprint]]: tool exposure does not by itself authorize concrete tool calls. | =ToolHardened= checks the actual agent and tool UID, trust score, namespace, and deployment stage for each request. The wrong-tool case is denied. |
| [[https://github.com/aws-samples/sample-cedar-agentic-ai-authorization][AWS agent sample]]: tool, delegation, and originating-user checks all contribute to a decision. | =authorizeFlow= constructs all three requests; =authorizeLayers= preserves each POO root, response, and policy evaluation errors. |
| [[https://github.com/cedar-policy/cedar/issues/2428][Cedar issue #2428]]: an erroring forbid can be skipped while another permit still allows. | =OriginUnsafe= reproduces an =Allow= with an error on malformed runtime context; =layersAllowed= rejects the compound flow. |

=ToolBase=, =DelegationBase=, and =OriginBase= intentionally allow a
support user's deletion request. Each hardened root overlays one policy:
=ToolHardened= checks the invoking agent, =DelegationBounded= checks depth
and requested capabilities against the target agent, and =OriginBounded=
checks the user role, MFA, and depth. =OriginRevoked= adds an explicit user
revocation veto. Ten flow cases separate the effect of user role, MFA,
delegation depth, capability, agent state, target tool, missing user, and
revocation. [[file:AgentDelegationExport.lean][AgentDelegationExport.lean]] sends
thirty-three individual layer requests to the official Cedar Rust
authorizer and checks the generated
[[file:AgentPolicies/originbounded.cedar][Cedar policies]]. Every POO root
also passes Lean Cedar schema and policy validation.

=OriginUnsafe= is a diagnostic counterexample, not a deployment revision.
Its policy is valid against a schema where =context.origin= is a User entity.
A caller that instead supplies a String at runtime causes the forbid to
error; Cedar's documented skip-on-error behavior leaves the broad permit in
effect. =malformedRawAllowsWithError= checks that raw result, while
=malformedFlowRejectedFully= checks that the compound API declines it.
This demonstrates why an =Allow= decision alone is insufficient when the
response also reports policy evaluation errors.

The host must authenticate the origin, verify delegation integrity, bind
capabilities and tool arguments to the proposed call, and reauthorize at
execution time. Cedar cannot verify a self-asserted context entity or
perform the tool call. The preprint's money ceiling and idempotency stages
are outside this deletion scenario.

* Why POO for three, four, and five authorization layers

This case asks how independently maintained tool, delegation, and origin
controls evolve when an enterprise adds routing and compliance agents,
freezes one delegation edge, then restores it. The
[[file:AgentChain.lean][AgentChain.lean]] model uses POO inheritance and C4 to
express those changes as small policy revisions shared by different path
lengths. The [[https://github.com/aws-samples/sample-cedar-agentic-ai-authorization][AWS reference sample]] supplies the three check categories and
delegation constraints; the longer paths and policy evolution are this
project's own modeled scenario.

| Path | Required checks | Result |
|------+-----------------+--------|
| Orchestrator to data bot | Tool, one delegation, origin = 3 layers | Admin with MFA can proceed. |
| Orchestrator to routing bot to data bot | Tool, two delegations, origin = 4 layers | The same delegation root checks both hops. |
| Orchestrator to routing bot to compliance bot to data bot | Tool, three delegations, origin = 5 layers | The old origin depth limit denies; =ChainGoverned= combines the revised controls. |

POO is useful here because the authorization topology evolves without
copying a Cedar policy for every chain length. =ChainDelegation= overlays the
original =DelegationBounded= policy once, generalizing its scope while keeping
its depth and target-capability check. The same root evaluates each hop.
=ChainOrigin= overlays only the originating-user policy to admit the third
hop, retaining Admin role and MFA. =ChainGoverned= uses C4 parent order to
compose the generic hop and revised origin policies in one root.
=ChainGovernedRevoked= extends one forbid for the routing-to-compliance edge;
other edges retain their policies.
=ChainGovernedRestored= removes that forbid after the incident without
editing or copying either inherited permit. The three-hop path becomes
available again, and its compiled Cedar policy set equals =ChainGoverned=.
The one- and two-hop paths stay available during the edge-specific freeze.

A second team can independently propose =ChainDepthOnly= from the older
=DelegationBounded= parent. It relaxes the same delegation policy ID and
would drop the delegator trust check. =ChainConflicted= deliberately combines
that sibling with =ChainDelegation=. Compilation rejects their competing
edits instead of silently choosing one branch. A real rollout must resolve
this conflict by making the intended override an explicit descendant.
This is a POO composition problem: copying Cedar policy text into each
chain length would not expose the shared edit ancestry or this conflict.

The =delegationEditLocal=, =originEditLocal=, =revokedEdgeLocal=, and
=restoredEdgeLocal= theorems identify exactly one changed policy ID per
revision. =conflictingDelegationEditsRejected= checks the conflict's policy
ID, and =restoredPoliciesEqualGoverned= checks exact rollback.
=unaffectedRootsFully=
checks that adding the chain modules leaves the existing tool and bounded
origin roots identical. This is policy-level locality; it does not claim that
an arbitrary external token chain or proof certificate is reusable.

The shared [[file:../../CedarPooSpec/CompoundAuthorization.lean][authorizeLayers API]] now caches each distinct POO root's
compilation within one compound request. A five-layer path evaluates three
delegation requests and one origin request against one compiled C4 root;
the tool check uses its own root. =compilationRootCountsFully= checks that
five layers require two distinct compiled roots. Every returned
layer still carries its own exact Cedar response and compilation equality.
=layerCountsFully= checks the 3/4/5 shape, =casesExactFully= checks thirteen chain
outcomes, and =allValidCasesErrorFreeFully= rejects hidden evaluation errors.
The [[file:AgentChainExport.lean][exporter]] compares fifty-two valid individual
requests with the official Rust Cedar authorizer and checks six generated
[[file:AgentChainPolicies/chaindelegation.cedar][Cedar revision artifacts]].

The host supplies an authenticated, complete delegation path, binds each hop
to its signed or otherwise verified delegation evidence, and enforces every
check before tool execution. =validPath= rejects repeated nodes and paths
outside this example's one-to-three-hop range. The model does not implement
HMAC, OAuth token exchange, or runtime loop detection across arbitrary
external agents.

* AI agent payment with per-call value authorization

[[file:AgentPayment.lean][AgentPayment.lean]] extends the agent authorization
model with a separate transfer decision for the concrete receiving account,
amount, and originating user. The motivation is the
[[https://arxiv.org/abs/2606.28679][ScopeGate preprint]]'s confused-deputy
case: exposing a payment tool to an agent does not authorize every value in
its arguments. [[https://genai.owasp.org/llmrisk/llm062025-excessive-agency/][OWASP's excessive-agency guidance]] likewise warns about excessive
tool permissions and missing approval for consequential actions. The roots
and values below are a fictive model of those problems, not a reproduction
of a published financial incident.

| POO root | Added decision boundary |
|----------+-------------------------|
| =FinanceTool= | Check the finance agent's identity, tool UID, trust, namespace, and production stage. |
| =PaymentBase= | Legacy transfer permit with no account or amount bound. |
| =PaymentScoped= | Overlay the permit so the receiving account belongs to the approved group. |
| =PaymentCapped= | Overlay a strictly positive amount at or below =100.0000=. |
| =PaymentHuman= | Overlay originating-user Admin role and MFA requirements. |

Each of eleven operations requires both =FinanceTool= and one payment root
through =CompoundAuthorization.authorizeLayers=. The cases show that a
tool-approved agent can still be denied an external destination, excessive
or zero amount, unprivileged origin, or missing MFA. A base operation with
an external account and large amount exposes the legacy gap; later roots
close one dimension at a time. The exact =100.0000= ceiling is allowed and
=100.0001= is denied. [[file:AgentPaymentExport.lean][The exporter]] sends
all twenty-two layer requests to the official Cedar Rust authorizer and
checks the five generated [[file:AgentPaymentPolicies/paymenthuman.cedar][Cedar policies]]. Every POO root also passes
Lean Cedar schema and policy validation.

The host must authenticate the originating user and agent, obtain account
group membership from an authoritative source, bind the transfer context to
the proposed transaction, enforce the conjunction, and make execution
atomic. Idempotency, replay prevention, human approval workflow, and the
integrity of those inputs remain host responsibilities. The case checks
authorization behavior; it does not claim to implement a payment processor.

* Cross-tool data flow for an AI agent

[[file:AgentDataFlow.lean][AgentDataFlow.lean]] models a separate enterprise
governance boundary: an agent may read an internal document but must not
thereby gain permission to publish its contents to a public repository.
The [[https://github.com/OWASP/OWASP-MCP-Governance-and-Risk-Project/blob/main/mcp-governance-risk-framework-v1.0.md][OWASP MCP Governance and Risk Framework]] describes a poisoned internal
wiki or tool response driving an agent to use another connected service for
data exfiltration. Cedar's [[https://docs.cedarpolicy.com/bestpractices/bp-authorization-patterns.html][authorization patterns]] explain that moving data
between containers calls for authorization at both the source and the
destination. The identities, documents, repository names, tenant, and review
facts in this example are fictive; the example models the cited failure mode
and authorization pattern rather than claiming to reproduce an incident.

| POO root | Control change |
|----------+----------------|
| =ReadBase= | Legacy agent read permit. |
| =ReadTenant= | Overlay tenant and originating-user role checks. |
| =PublishBase= | Legacy agent publication permit. |
| =PublishScoped= | Overlay source and destination tenant equality. |
| =PublishClassified= | Overlay a classification rule: internal material may go only to an internal destination. |
| =PublishReviewed= | Overlay independent Security reviewer, MFA, and approval for public publication. |
| =PublishRevoked= | Extend a specific source-document publication veto. |

Thirteen operations cover a legacy internal-to-public leak, foreign source
and destination tenants, an internal document sent to a public repository,
public material with and without review, a reviewer with the wrong role,
self approval, an unprivileged originating user, internal publication, and
revocation. =classifiedLeakBoundaryFully= establishes that the read layer
allows the internal document while the publication layer denies the public
destination. =casesErrorFreeFully= checks that none of the well-formed cases
rely on Cedar policy evaluation errors for their outcomes.
[[file:AgentDataFlowExport.lean][The exporter]] compares all twenty-six
individual layer responses with the official Rust Cedar authorizer and
checks the seven generated [[file:AgentDataFlowPolicies/publishreviewed.cedar][Cedar policies]]. Every root passes Lean Cedar
schema and policy validation.

The host must authenticate the agent, original user, and reviewer; provide
authoritative tenant, classification, and approval facts; and bind both
authorization requests to the exact bytes and destination of one proposed
publication. It must enforce the combined decision at the write boundary.
The example does not inspect document contents, prove provenance of these
facts, or implement an MCP server.
