#+TITLE: Agent Payment
#+OPTIONS: toc:nil

* AI agent payment with per-call value authorization

[[file:AgentPayment.lean][AgentPayment.lean]] extends the agent authorization
model with a separate transfer decision for the concrete receiving account,
amount, and originating user. The motivation is the
[[https://arxiv.org/abs/2606.28679][ScopeGate preprint]]'s confused-deputy
case: exposing a payment tool to an agent does not authorize every value in
its arguments. [[https://genai.owasp.org/llmrisk/llm062025-excessive-agency/][OWASP's excessive-agency guidance]] likewise warns about excessive
tool permissions and missing approval for consequential actions. The roots
and values below are a fictive model of those problems, not a reproduction
of a published financial incident.

| POO root | Added decision boundary |
|----------+-------------------------|
| =FinanceTool= | Check the finance agent's identity, tool UID, trust, namespace, and production stage. |
| =PaymentBase= | Legacy transfer permit with no account or amount bound. |
| =PaymentAccount= | The account owner forbids transfers outside the approved account group. |
| =PaymentAmount= | Treasury independently forbids zero, negative, or above-ceiling amounts. |
| =PaymentOrigin= | The identity owner independently forbids callers without Admin role and MFA. |
| =PaymentGoverned= | C4 composes the three sibling controls and the inherited permit. |
| =PaymentFrozen= / =PaymentRestored= | Freeze one approved account, then remove that one veto without rewriting any parent. |

Each of sixteen operations requires both =FinanceTool= and one payment root
through =CompoundAuthorization.authorizeLayers=. The branch probes expose
why no one owner can publish the final policy alone: the account branch still
admits an excessive amount and an unprivileged origin, the amount branch
still admits an external account, and the origin branch still admits an
excessive amount. =PaymentGoverned= denies all three. The exact =100.0000=
ceiling is allowed and =100.0001= is denied. Freezing the approved account
leaves a second approved reserve account available; removing the freeze
restores exactly the earlier compiled policy set.

The example's =policySlot= and =freezeSlotEvolution= inspect Lean-POO's
public compiled C4 plan before publication. They show the inherited permit,
all three sibling vetoes, the new freeze veto, and the =some none= tombstone
that masks that veto at =PaymentRestored=. The
[[file:../../../../Tests/Enterprise/Agent/Payment/CompiledPlan.lean][separate regression file]] checks those exact slot values. The normal
=Model.compile= path still validates edit intent and sends the resulting
policy list to Cedar; raw slot inspection does not authorize a request.

=accountBranchLocal=, =amountBranchLocal=, and =originBranchLocal= identify
one new policy ID per owner. =governedPolicyIdsFully= checks that C4 emits
one inherited permit and three independent vetoes. =freezeEditLocal= and
=restoreEditLocal= isolate the emergency change to one ID;
=restoredPoliciesEqualGoverned= checks exact rollback. The
[[file:AgentPaymentExport.lean][exporter]] compares thirty-two well-formed
layer requests and two malformed-context layer requests with the official
Cedar Rust authorizer, and checks eight generated
[[file:AgentPaymentPolicies/paymentgoverned.cedar][Cedar revision artifacts]].
Every POO root also passes Lean Cedar schema and policy validation.
=malformedOriginRejectedFully= demonstrates the runtime boundary: Cedar's
raw transfer response can be =Allow= with an erroring veto if the host sends
an origin String instead of a User entity. =layersAllowed= rejects the whole
operation because it checks policy errors as well as the decision.
A downstream caller using the generated =.cedar= policies must enforce the
same error check.

The [[file:ValidatedExport.lean][schema-bound exporter]] projects the Lean
payment schema into Cedar's public JSON form and checks all thirty-two
well-typed layer requests through strict Rust Cedar policy, entity, context,
and request validation. Its distinct receipts include a schema digest.
The malformed origin requests remain only in the diagnostic manifest because
schema validation must reject them. See
[[file:../../../../docs/rfc/0006-schema-bound-cedar-replay.org][RFC 0006]].

The host must authenticate the originating user and agent, obtain account
group membership from an authoritative source, bind the transfer context to
the proposed transaction, enforce the conjunction, and make execution
atomic. Idempotency, replay prevention, human approval workflow, and the
integrity of those inputs remain host responsibilities. The case checks
authorization behavior; it does not claim to implement a payment processor.

The [[file:AuthorizationDelta.lean][authorization-delta example]] also checks
the entire schema-defined authorization space for two changes. Adding the
emergency freeze produces no new Allow across four request types. Removing
that freeze produces a concrete new-Allow/old-Deny witness, which the official
Rust Cedar authorizer replays. This verifies the global direction of each
policy revision within the schema, beyond the sixteen fixed operations above.
The solver boundary is specified in
[[file:../../../../docs/rfc/0004-authorization-delta.org][RFC 0004]].
