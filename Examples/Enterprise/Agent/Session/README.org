* Research case and exact boundary

[[https://arxiv.org/abs/2608.15888][Bounded Agents (2026)]] studies a failure of
per-request agent authorization: individually permitted actions can compose
into a prohibited outcome. Its proposed Agentic Principal Chain accounts
for delegation, prior actions, budgets, and compositional restrictions. The
paper's soundness argument assumes complete restrictions and serialized
admission. This example explores a narrow Cedar/POO projection of that
problem; it does not implement or reproduce that paper's full mechanism.

[[https://ojs.aaai.org/index.php/AAAI-SS/article/view/36899][EchoLeak]]
describes an indirect prompt-injection path in which untrusted content
could steer an assistant toward data exfiltration under particular
conditions. [[https://www.microsoft.com/en-us/security/security-insider/emerging-trends/ai-application-security-considerations-for-organizations][Microsoft's security analysis]]
states that the reported vulnerability was fixed. This case models the
authorization boundary that should check a proposed read and external send;
it does not reproduce the exploit or detect injected instructions.
[[https://www.anthropic.com/threat-intelligence-report-september-2026][Anthropic's
September 2026 threat intelligence report]] documents increased use of AI
to automate parts of malicious campaigns. It motivates the repeated-probe
trace here, without implying that the report evaluated this model.

| Source observation | Proposed Cedar/POO projection | Unverified boundary |
|--------------------+-------------------------------+---------------------|
| Independent read and send grants can compose into exfiltration. | A trusted host passes prior sensitive-read state into each Cedar request; a History owner vetoes external send after that read. | The host must observe all relevant reads and bind the sent bytes to the checked action. |
| A delegated task can be exceeded without violating a broad send grant. | An Intent owner vetoes a send whose proposed intent differs from the delegated intent. | The model does not infer intent or authenticate the declaration. |
| Automated proposals can repeatedly exercise an allowed capability. | A Budget owner limits the count of accepted external sends in the session. | The host must serialize decision and ledger update across workers. |
| Incident response and recovery change one control. | Incident extends an external-egress veto; Recovered removes only that veto. | An external incident process decides when recovery is safe. |

The identities, documents, endpoints, task names, and export limit in
[[file:BoundedSession.lean][BoundedSession.lean]] are illustrative. Cedar
evaluates one request at a time. The =Session= ledger and =replay= transition
are a proposed host protocol: the host supplies authenticated facts, checks
before effect, advances state only after Allow, and serializes the whole
admission transaction. Neither Cedar nor Lean-POO alone prevents prompt
injection, proves the host protocol is deployed correctly, or guarantees
complete coverage of all tools and data flows.

* POO decision matrix

=A= means Allow and =D= means Deny. Each row starts with a fresh session.
The named Lean traces are exported step by step to the official Cedar Rust
authorizer with the pre-admission context for each request.

| POO root | Read sensitive, then external send | Off-task external send | Second external send after one accepted | Internal send after sensitive read |
|----------+------------------------------------+------------------------+-----------------------------------------+------------------------------------|
| =Base= | A, A | A | A | A |
| =Intent= | A, A | D | A | A |
| =History= | A, D | A | A | A |
| =Budget= | A, A | A | D | A |
| =Integrated= | A, D | D | D | A |
| =Incident= | A, D | D | D | A |
| =Recovered= | A, D | D | D | A |

The three independent branches each close one hole and leave the other two.
=Integrated= C4-composes the controls without copying their policy sets.
=Incident= stops even a first otherwise valid external report; =Recovered=
restores that report while retaining all three permanent controls.
Rejected off-task sends do not spend the budget. In the 32-proposal trace,
one ordinary external send is accepted and the following 31 are denied.
These are finite model decisions, not a claim that all future attacks are
blocked.

not hidden session states.

* Authorization delta over a finite session trace

[[file:AuthorizationTraceDelta.lean][AuthorizationTraceDelta.lean]] uses the
public [[file:../../../../CedarPooSpec/AuthorizationDeltaTrace.lean][trace-delta API]] to replay the *same proposed actions* under =Base=
and =Integrated=. Each side carries its own state forward only after an
error-free Cedar Allow. A sensitive read followed by external send changes
=[Allow, Allow]= to =[Allow, Deny]=. In a separate four-proposal trace, the
integrated budget denies the second and third external sends; the old root
continues to spend its ledger. The final proposals are the same operation,
but their Cedar contexts differ because prior decisions changed the states.
The trace marks the second external send as a direct policy difference:
both roots receive exactly the same Cedar request and entities. At the third
send, the inputs differ, so its changed decision cannot be assigned solely
to the policy revision. The equality check includes the full entity store,
not only the request context. The sensitive-read veto is also a direct
difference at an identical Cedar input.
The trace additionally evaluates both policies on *both* observed inputs.
At the final budget proposal, =Base= allows and =Integrated= denies at
either input: the changed ledger does not change either policy's decision
there. A second two-step trace first proposes an off-task external send.
=Base= accepts it and spends one export; =Integrated= denies it and spends
none. Both allow the following on-task send, masking a policy difference
that appears when both policies are evaluated on the old ledger's input.
Under =Integrated=, moving to its own unspent-ledger input changes Deny to
Allow. These cross-evaluations compare concrete Cedar snapshots; they do
not simulate the alternative Host trajectory. A Lean theorem expresses the
actual decision difference as the Boolean exclusive-or of the policy change
at the old input and the input change under the new policy. In this masked
case both terms are true, so the observed decisions agree.
The API rejects a Host projection that silently substitutes a different
operation at that point. The report retains the C4 History owner and proof
footprint.

The bounded extension enumerates all nonempty lists of length at most three
over the explicit choices =readSecret=, on-task =sendExternal=, and off-task
=sendExternal=. It checks 39 proposal lists from a fresh session, including
denied proposals that leave the ledger unchanged. None has an Allow gain
from =Base= to =Integrated=. Thirty-three lists contain a direct loss at an
identical Cedar input, and sixteen contain a loss after the two inputs
diverge; those sets overlap. Five lists contain an input-driven decision
change under =Integrated=; none do under =Base=. The 102 bounded steps and
eight named-trace steps each produce four Cedar decisions: both policy roots
at both observed inputs. All 440 decisions are replayed by official Cedar
Rust.
The API rejects a case cap below 39 before constructing the lists. This is
exhaustive only for those three choices, that initial state, and that
three-step horizon; it says nothing about other actions or longer runs.
The generic generator has a Lean proof that a length-=n= enumeration contains
exactly =alphabet.length ^ n= entries. The example also checks the three
level counts =3, 9, 27=.

[[file:HostSafety.lean][HostSafety]] goes beyond that three-step enumeration
for a fixed five-operation alphabet (public read, sensitive read, external
send, internal send, and off-task external send). Its =Receipt= contract binds
each operation to the prior committed =Session=, exact Cedar request and
error-free decision, and Host ledger effect. Lean induction proves that every
finite serialized receipt chain from the default ledger stays in four concrete
states. A second theorem proves that an allowed external send in any such
reachable state has not seen a sensitive document and has not spent its one
export. The transition cases use the actual =Integrated= Cedar decision.
The executable =run= constructs a valid receipt chain for every operation
list, and =runEqReplayFinal= proves its final ledger equals the existing
=replay= implementation for the same operations.
The Host must authenticate the ledger and effect receipts and enforce the
listed operation mapping; Lean cannot infer those properties from a prompt or
tool output.

This addresses a finite observation raised by [[https://arxiv.org/abs/2608.15888][Bounded Agents]]: independent
request checks miss effects of earlier actions. The September 2026
[[https://arxiv.org/abs/2609.15803][study of sequential agent authorization]] goes further and analyzes safety
over possible future state transitions. This is an arbitrary-length invariant
for its declared alphabet and initial ledger, not a universal claim for every
Host action or state. The proposal sequence, request projection, and state
transition are supplied by the Host model; real execution still requires
authenticated facts, complete tool coverage, serialized admission, and
effect receipts.

* Composition and proof receipts

| Root | Owner-local edit | Materialized policy bodies | Fresh body work against stated baseline |
|------+------------------+----------------------------+----------------------------------------|
| =Base= | Extend read and send grants | 2 | 2 |
| =Intent= | Extend delegated-intent veto | 3 | 1 vs =Base= |
| =History= | Extend read-then-egress veto | 3 | 1 vs =Base= |
| =Budget= | Extend cumulative-export veto | 3 | 1 vs =Base= |
| =Integrated= | C4-compose Intent, History, Budget | 5 | 3 vs =Base= |
| =Incident= | Extend external-egress freeze | 6 | 1 vs =Integrated= |
| =Recovered= | Remove only the freeze | 5 | 0 vs =Incident= |

Seven standalone Cedar revisions contain 27 materialized policy
occurrences. Lean declares six distinct policy bodies and seven local edits,
including the recovery removal. This counts source structure, not a measured
speedup. Lean proves the incident adds exactly one fresh policy body and
recovery adds none. The unchanged certificates are reused when the
authorization certificate is reclosed; Cedar's upstream soundness theorem
applies to the resulting snapshot. The
[[file:BoundedSessionExport.lean][exporter]] materializes every named step
and the Rust bridge compares its expected authorization result to the
official Cedar engine after rendering and reparsing the policy set.
