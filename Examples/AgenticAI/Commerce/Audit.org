* Audit findings

** A1: authority synchronization is still an adapter premise

=claim_dispatch= refreshes authority inside the commit callback. Its
=DispatchPermit= carries the request, not a durable root cut or an enforceable
provider fence. =PaymentProviderPort= documents synchronization through actual
release, but the type signature cannot establish that a suspended adapter obeys
it. This is a declared implementation obligation, not a newly demonstrated
exploit. Principal-level =policy_epoch= must not silently stand in for a
root-mandate revocation generation: their scope and update authority differ.

Specify the provider acceptance linearization point. A retired root must not
be accepted after that provider's fence. Work admitted before the fence can
complete afterward and needs accounting; cancellation is not payment rollback.
Start with the current single-root lineage. Multi-root support algebra is a
later extension requiring its own semantics and evidence.

** A2: consumption safety currently trades away recovery liveness

A persisted claim followed by process death destroys the only permit. Neither
an exact claim replay nor a provider =NotSent= result reopens the purchase.
This prevents duplicate release in the reference design, but can strand it.
An =Unknown= status must retain the exact operation and request binding.

An outbox/recovery design needs an immutable request, durable attempt ownership,
a current acceptance fence, and an independently declared provider deduplication
and retention contract. It cannot recreate a fresh unrestricted permit from the
old credential. Without those endpoint capabilities, blocked/unknown is the
correct observable result; eventual payment is not guaranteed.

** A3: receipt authenticity does not establish settlement or fulfillment

The current =succeeded/rejected= receipt model has no rail-specific finality
predicate or service-delivery evidence. Give each profile a typed meaning for
accepted, finalized and fulfilled, with independently trusted issuers and exact
transaction correspondence. Do not reinterpret the existing success receipt
as cleared funds or completed delivery.

** A4: signed claims can faithfully bind a manipulated selection

Current signature and projection checks protect the supplied transaction.
They do not establish that the agent's earlier tool results or selected seller
faithfully reflected the principal's task. Evaluate pre-signature manipulation
as a separate Host/Case experiment with an independent intent oracle. Preserve
both a legitimate-success control and a signed-but-task-inconsistent witness.

** A5: AP2 presentation is a separate protocol lifecycle

The existing synthetic budget admits several different purchases. The inspected
[[https://raw.githubusercontent.com/google-agentic-commerce/AP2/main/docs/ap2/specification.md][AP2 specification]] requires the shopping agent to obtain a rejection receipt
before another open Checkout/Payment Mandate presentation. A future protocol
profile must bind the correct mandate, checkout and role-specific receipt, and
match exact schema versions. Pin the upstream source commit before implementing
this profile. Budget consumption does not implement its presentation rule.

The nonce-window paper's throughput and latency are not measurements of this
implementation. A TTL safe for one expiring nonce does not determine the
retention horizon of our scope/purchase tombstone. Prove that no currently
acceptable credential, replay, restored snapshot or provider retry can reopen
the slot before reclaiming that record.

The existing [[https://arxiv.org/abs/2604.15367][Agentic Commerce SoK]] remains a threat-map background source;
it is not an implementation recipe or conformance proof. [[https://www.agenticcommerce.dev/docs/reference/payments][ACP Delegate Payment]]
specifies idempotent token creation, which must be distinguished from deduplication
of payment release, final settlement and service delivery.

* Revised implementation order

** P0: freeze the proof and source correspondence

Create a property matrix with source/version, role, exact bound fields,
acceptance event, invariant, code location and positive/negative trace. Classify
each guarantee as proved in Lean, checked locally, required of a backend/provider,
or unimplemented. Start with the existing synthetic profile; add one pinned
protocol profile before claiming AP2/ACP/MPP conformance.

** P1: model acceptance-time authority and fence it

Cedar owns the pure root-generation and protected-acceptance transition.
MRR/Host consumers own fence persistence, authority observation and endpoint
adapters. Require a durable binding between request, root lineage and the
acceptance generation. Test a current success case, a suspended old request,
key/revocation changes, stale-worker restart and an unrelated-root control.
An endpoint without an authenticated acceptance barrier cannot establish the
post-fence claim. Do not compare unrelated issuer/provider counters as one clock.

** P2: define recovery before selecting a production backend

Specify claim, dispatch attempt, provider acceptance, unknown, rejected and
finalized states. Add a provider-free deterministic failure harness in the MRR
integration, then expose those same probes as conformance requirements for
external storage/provider adapters. MRR stays the protocol/interface owner;
this plan does not choose or embed a DB.

| Injection point | Required observation |
|-----------------+----------------------|
| Before claim commit | No accepted effect and no false confirmed claim |
| Head/receipt durable, ACK lost | Exact operation recovery; no second debit or new unrestricted permit |
| Claim ACK received, process dies before send | Explicit stranded state under today's API; future resumption needs a fenced durable ownership rule |
| Provider accepts, reply lost | Unknown with the original provider, key and body; never retry through another provider |
| Signed receipt received, local persistence lost | Authenticate and recover the same receipt; no fresh purchase claim |
| Root retired after permit creation | Old-root acceptance after the installed sink fence is refused |
| Consumption record reclaimed | Old/reissued credentials cannot reopen the logical purchase |
| Same operation ID, different body | Conflict, regardless of replay order or worker restart |

Check =acceptedEconomicEffects(scope,purchase) <= 1= only against an explicitly
instrumented provider acceptance oracle. A client API call count is not that
oracle. Progress requires declared endpoint/query availability and retry support.

** P3: add protocol-specific presentation and evidence

For the first selected wire profile, verify exact schema versions, issuer roles,
canonical checkout binding and presentation/acceptance/rejection receipts.
Add settlement-finality and fulfillment/compensation rules as separate layers.
Implement parsing and semantic correspondence in Cedar domain/Case packages;
persist profile state and integrate content through MRR consumers.

** P4: evaluate agent selection and acquired capability

Run deployment-specific pre-signature prompt injection, seller substitution and
tool-result poisoning with matched benign controls. Measure false accepts,
false rejects and reviewer burden. For resource purchases, later extend the
Case with quarantined output, authenticated capability resolution and explicit
activation. Payment approval alone cannot activate a new credential or agent.

* Next concrete slice

Start P0 and the single-root part of P1. The first deliverable should be a small
Lean acceptance/fence model, its explicit bridge obligation, and the delayed
permit trace that the current interface leaves to the provider contract.
Preserve today's replay/unknown fail-closed behavior until a reviewed P2
recovery contract justifies any new durable resumption transition.

* Implementation follow-up

The single-root P0/P1 slice is implemented in the [[file:Properties.org][property correspondence matrix]].
Provider-local fences now bind fresh consumption permits to the root generation
and exact provider/request. Deployment assumptions and recovery gaps remain
explicit; this does not establish a global quiescence certificate.

* Recovery implementation follow-up

The [[file:Recovery.org][dispatch recovery protocol]] persists original root authority in the
consumption request and adds provider ownership CAS, exact recovery and dual
fence acceptance. Previously stranded acknowledged claims can be resumed only
through an endpoint implementing the durable ownership contract.
