#+TITLE: Agentic AI Commerce: Delegated Intent Before Payment
#+OPTIONS: toc:nil

* Thesis and boundary

As of 2026-10-02, the strategic object here is a principal's bounded task
delegated to an identified agent. The agent may discover a seller, select an
offer, and request a purchase while the principal is absent. A payment rail
executes a later, narrower instruction. The trust question is whether the
agent's exact choice is inside its current authority and corresponds to the
merchant's actual offer. This repository models that question separately from
processor acceptance, settlement, and bank clearing.

The public [[file:../../../CedarPooSpec/AgenticAI/Commerce/Budget.lean][Commerce Budget]] kernel represents a verified mandate, a verified
merchant offer, exact selected purchase terms (including an opaque checkout
commitment), and one mandate's cumulative
budget. It admits a purchase only when agent identity, mandate ID, merchant,
product, offer, amount, asset, policy epoch, expiry, revocation state, and
remaining budget agree. The budget also retains the *whole active mandate* so
the same ID cannot silently acquire another principal or a wider scope. A
successful reservation stores the complete purchase
and increments a revision. The Host must authenticate both input assertions
and persist that revision with compare-and-swap before issuing any credential
or payment request. The [[file:../../../Tests/AgenticAI/Commerce/Admission.lean][regressions]] exercise substitution, replay, stale
authority, revocation, and budget boundaries. Run =just check-agentic-ai-commerce=.

Amounts are natural-number minor units in this abstract kernel. An asset
adapter must define the unit, supported assets, and conversion to an actual
payment instrument. The model does not sign mandates, authenticate merchant
quotes, issue agent-specific tokens, perform identity proofing, detect fraud,
publish policy, or execute a purchase. Its =verified= flags are Host assertions.
Its multi-purchase budget is a synthetic local contract, not AP2 conformance.
The checkout commitment is an opaque value until the Host computes and verifies
it against a canonical merchant checkout.

The public [[file:../../../CedarPooSpec/AgenticAI/Commerce/Delegation.lean][delegation kernel]] additionally checks that each child Agent can only
narrow the preceding mandate's merchant, product, per-purchase, cumulative,
asset, principal, policy epoch, and expiry constraints. It resolves an exact
chain of parent snapshots and issuer Agent identities, and refuses reuse of
an ancestor mandate ID, Agent ID, or Agent key. Its =verified= flag
still asserts Host authentication. The public
[[file:../../../CedarPooSpec/AgenticAI/Commerce/SharedBudget.lean][shared budget]] now charges the principal root and every ancestor for each
accepted purchase across delegated branches. It retains exact lineages, refuses
mandate ID rebinding and global purchase/offer replay, propagates ancestor
revocation, and rejects stale root revisions. The Lean model proves revision
advance, stale-revision refusal, and root-cap preservation.

The optional Rust [[file:../../../rust/src/agentic_ai/commerce/budget_commit.rs][budget bridge]] checks exact Lean before/after claims, fresh
signed authority, root and ancestor spend, and the current content CID. It
uses MRR Data's conditional commit protocol to propose one head replacement
with an exact revision and operation ID. The async commit entry point now uses
a Host-supplied transaction port, refreshes authority inside its validation
callback, and separates confirmed commit, exact replay, and unknown outcome.
The signed consumer races two children, refuses over-cap retry, and recovers a
lost acknowledgement under the original operation without a second reservation.
These checks execute no DB transaction:
the backend must authenticate its inputs and atomically persist the head and
operation receipt. =just check-agentic-ai-commerce-admission= checks this bridge
with JSON emitted by Lean.

The public [[file:../../../CedarPooSpec/AgenticAI/Commerce/Credential.lean][credential boundary]] requires a credential to name the exact
committed reservation, shared scope, operation, before/after content IDs and
revisions, full authority lineage, checkout, issuer, and expiry. Current ancestor
revocation denies a descendant credential even when its original receipt remains
available. A later head retaining the exact reservation does not charge it again. The [[file:../../../CedarPooSpec/Vertical/FinancialServices/AgenticCommercePayment.lean][public HKD cents adapter]] checks that those objects
correspond to a downstream =PaymentOperation=, including payer, merchant,
amount in canonical cents, agent, mandate, nonce, and checkout commitment.
The latter field is optional for generic payments but mandatory in this
adapter. A matching envelope is *not* a Cedar Allow or an instruction to send
funds. The Host still verifies signatures, applies policy, ensures durable
single use of the credential, and binds the same checkout to the provider's
real request and response.

The optional Rust [[file:../../../rust/src/agentic_ai/commerce/signatures.rs][mandate and offer verifier]] checks raw P-256 ECDSA signatures
over domain-separated, length-prefixed mandate, child delegation, and offer
payloads. Its trust table maps the complete Cedar principal UID components or
a merchant ID to a public key. The principal-signed mandate binds the Agent's
public key; that parent Agent key must sign each child grant. The offer verifier
also recomputes SHA-256 over the exact checkout bytes. Positive and
altered-agent, altered-principal, altered-price, altered-checkout,
wrong-issuer, widening-child, and ancestor-identity-reuse cases are executable under the
=agentic-ai-commerce-signatures= Cargo feature, which =just check-rust= covers. This is a
local versioned encoding, not AP2 JWT or a live issuer integration. The Host
must map *every* verified Rust field to the corresponding Lean object before
setting =verified=, and must manage key enrollment, rotation, and revocation.
The optional [[file:../../../rust/src/agentic_ai/commerce/projection.rs][projection API]] now checks all signed mandate and offer fields against
the [[file:../../../CedarPooSpec/AgenticAI/Commerce/Projection.lean][public Lean claims]]. =just check-agentic-ai-commerce-projection= tests a Lean JSON
fixture against live Rust verified values and individually changes each field.
This establishes field correspondence for the synthetic fixture; the Host
still owns the live admission decision and dynamic checks.
The optional [[file:../../../rust/src/agentic_ai/commerce/admission.rs][process-local admission reference]] now re-verifies the signed root mandate,
each parent-agent-signed child, and the merchant offer on each call against
current enrolled keys, time, policy epoch, ancestor and child revocations,
exact Lean lineage claims, and a Host policy callback. The clock, policy
evaluator, and registry updates are trusted Host inputs. This establishes
process-local delegated admission for the synthetic fixture; it neither
authenticates a live Agent request nor makes the registry and budget durable.

The common engineering inference is that *agent recognition*, *delegated
purchase authority*, *merchant price integrity*, and *payment execution* are
independent facts. None implies the next. This is why the optional Rust module
is named =agentic_ai::commerce::signatures=: it authenticates only the signed mandate,
delegation, and merchant offer payloads plus checkout bytes. The public Lean
model then checks structural scope and purchase correspondence, subject to a
Host mapping and durable state. No cross-protocol conformance is claimed.

* Protocol and research implications

[[https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md][AP2 v0.2]] distinguishes human-present approval of a closed
checkout from autonomous operation under open mandates. In the latter, an
agent key signs a closed mandate and verifiers check the user-authorized
constraints; checkout and payment mandates bind to a merchant-signed checkout.
AP2 describes agent-to-agent mandate delegation as outside its current scope.
This motivates exact offer binding and a separate future study of multi-agent
attenuation; this synthetic kernel does not implement AP2 JWTs or its
single-open-mandate presentation rule.

AP2 further requires exact mandate schema version matching, deterministic
verification by each role, and signed acceptance or rejection receipts. An
autonomous Shopping Agent must wait for a rejection receipt before presenting
a subsequent open Checkout or Payment Mandate. The present multi-purchase budget
is deliberately a different contract; it cannot be presented as AP2's
one-outstanding-presentation lifecycle. At dispute time, AP2 links both mandate
receipts back to the exact signed checkout and payment mandates. The current
=checkoutCommitment= and =PaymentOperation= fields only preserve local
correspondence; they do not supply those independently signed artifacts.

[[https://arxiv.org/abs/2609.00060][A Formal Analysis of Agent Payment Protocols]] (2026 preprint) studies x402,
MPP, ACP, and AP2 and finds cross-actor, cross-stage binding questions between
intent, authority, payment, and service effects. [[https://arxiv.org/abs/2604.15367][SoK: Security of Autonomous
LLM Agents in Agentic Commerce]] (2026 preprint) adds agent integrity,
inter-agent trust, market manipulation, and regulatory exposure to the threat
map. These are research results and proposed taxonomies, not proof of a
specific production exploit or validation of this implementation.

* Commit-to-credential research slice (2026-10-02)

[[https://ap2-protocol.org/ap2/implementation_considerations/][AP2 implementation considerations]] assign mandate verification and payment-token
release to the credential provider, and distinguish merchant checkout receipts
from processor payment receipts. The [[https://www.agenticcommerce.dev/docs/reference/payments][ACP Delegate Payment reference]] scopes
allowances by amount, currency, checkout session, merchant, expiry, and one-time
reason; its idempotency key addresses duplicate token creation. These motivate
separate commit, credential-admission, and effect/receipt gates in this model.
Neither protocol specifies our synthetic shared-budget content-head format.

The [[https://arxiv.org/html/2609.00060v1][formal analysis of agent payment protocols]] studies cross-stage relations
under explicitly modeled trust boundaries. Its counterexamples and implementation
witnesses have different evidence levels; they are not a production-wide failure
claim. We use this distinction to ask whether an authenticated earlier commit
still authorizes the exact current credential and checkout. We do not import its
Tamarin results as proofs of this Lean/Rust implementation.

The optional Rust [[file:../../../rust/src/agentic_ai/commerce/credential.rs][credential validator]] recovers an exact MRR operation receipt,
verifies raw previous/committed block CIDs and the original one-reservation
transition, and rechecks fresh signed root/delegations, policy, merchant offer,
checkout bytes and independently enrolled issuer key. All projected verification
flags are omitted. Lean proves accepted credentials retain a current reservation
and an authenticated commit, with explicit negative cases for ancestor revocation,
future revision, wrong scope/operation, expiry and checkout substitution.

The [[file:../../../rust/tests/integration/agentic_ai/commerce/credentials.rs][signed consumers]] test proposal-only and unreadable-ledger rejection, later-head
retention/removal, issuer rotation/revocation, signed claim tampering, changed
checkout/price, current cap violations and policy/mandate revocation. The two
opaque CIDs in the Lean credential template are filled from actual Rust content
bytes; every semantic receipt field is taken directly from the exported fixture.
The serialized provider remains test-only. These checks establish local admission
correspondence, not AP2/ACP conformance, durable credential consumption, payment
execution, fulfillment, or dispute verification.

* Single consumption and provider binding slice (2026-10-02)

[[https://www.agenticcommerce.dev/docs/reference/payments][ACP Delegate Payment]] provides scoped allowances and token-creation idempotency;
that does not establish one economic effect for our custom credential. [[https://ap2-protocol.org/ap2/implementation_considerations/][AP2]] assigns
payment-mandate checks and signed payment receipts to different verifier roles.
We therefore specify a separate [[file:../../../CedarPooSpec/AgenticAI/Commerce/Consumption.lean][consumption ledger]] keyed by budget scope and
purchase, independent of credential ID and provider. Its proved duplicate refusal
applies regardless of the provider outcome. The [[file:../../../rust/src/agentic_ai/commerce/consumption.rs][Rust claim]] reuses the existing
MRR conditional port, authenticates the original reservation receipt, compares
exact raw ledger CIDs and proposals, and refreshes budget/issuer/mandate authority
inside validation. The backend must serialize those changes through release.

A newly confirmed claim yields one move-only release permit. Exact replay,
uncertain commit and recovery cannot reconstruct it. The [[file:../../../rust/src/agentic_ai/commerce/provider.rs][provider interface]] carries
the complete exact request with a stable scope/purchase idempotency key, and
verifies a signed receipt's full-request commitment against an independently
enrolled provider key. Status recovery performs no payment and cannot grant a
fresh credential or retry. The [[file:../../../rust/tests/integration/agentic_ai/commerce/consumption.rs][test-only consumers]] check two competing claims,
reissued credentials/providers, uncertain claim/payment ACKs, fresh revocation,
changed receipt/request, and key rotation. No production provider is connected.

This gives bounded local single-release safety, not eventual or exactly-once
economic execution. A crash after claim but before dispatch may block the purchase;
a known non-release or absent provider status also does not reopen it. A deploying
adapter needs a fenced retry/recovery protocol with provider-enforced idempotency,
authenticated status and live-authority synchronization. Fulfillment and dispute
receipts require their own issuers and correspondences.

* Next code and evaluation slices

1. Bind the process-local delegated admission reference to authenticated
   clock, key, policy, and revocation sources. Recheck the complete signed
   lineage within a durable shared-budget reservation transaction; a stale
   root, parent Agent key, or child grant must fail before reservation.
2. Specify a separate presentation ledger for protocols that require a
   single outstanding open mandate. Test a second presentation without a
   matching signed rejection receipt, a forged receipt, and a receipt for a
   different checkout. Keep this separate from the synthetic multi-purchase
   budget rather than quietly changing its semantics.
3. Connect the proved shared-root revision and cap rules to a backend's atomic
   transaction. The pure Lean model and MRR Data conditional commit protocol
   are implemented; the Rust bridge checks exact Lean before/after claims.
   MRR Data is an interface for content and conditional publication. A backend
   must persist one head and exact operation receipt atomically, then test two
   child writers racing under the same root and recovery after an uncertain ACK.
4. Credential admission, single consumption, provider request and signed receipt
   contracts are implemented with test-only providers. Connect a production
   sandbox and durable ledger; validate crash-after-claim recovery, fenced retry,
   provider-enforced idempotency and authority changes during suspended release.
   Then bind fulfillment and dispute evidence to independently trusted issuers.
5. Evaluate prompt injection, seller substitution, collusion, and model drift
   with measured detection quality and reviewer load. A passing fixture does
   not establish operational risk performance.
