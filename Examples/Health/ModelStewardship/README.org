#+OPTIONS: toc:nil

* Question exercised

When two hospitals contribute longitudinal records to a medical model, what
must be reconsidered if one source is withdrawn from this use? The
[[file:../ModelStewardship.lean][Lean scenario]] registers synthetic source,
dataset, training-run, checkpoint, deployment, and inference artifacts. The
[[file:../../../Tests/Health/ModelStewardship.lean][regressions]] check the exact
affected branch while preserving a model trained only on hospital A data.

* POO composition and checked behavior

=Training=, =Publication=, and =Clinical= independently introduce Cedar
permits. =Lineage= introduces the reusable
[[file:../../../CedarPooSpec/Data/LineageUse.lean][LineageUse]] veto, binding
artifact identity, lineage revision, and Host-projected availability to all
three actions. =MedicalModel= mixes these owners using LeanPOO. =ModelIncident=
extends the result with a local publication and inference veto; =Recovered=
withdraws that incident policy slot. The incident leaves the training owner
unchanged.

[[file:Admission.lean][Admission]] projects each Cedar request from an exact
training, publication, or inference =Effect= and a =Snapshot=. It uses the
public [[file:../../../CedarPooSpec/Admission/BoundOperation.lean][BoundOperation]]
API to reject an effect or snapshot substituted after preparation. The
[[file:../../../CedarPooSpec/Governance/ScopedApproval.lean][ScopedApproval]]
grant binds actor, operation, purpose, source, destination, governance
revision, and expiry. The public
[[file:../../../CedarPooSpec/Data/ArtifactAssessment.lean][ArtifactAssessment]]
claim binds an assessment kind, artifact, exact selected digest, governance
revision, result, and expiry. Training requires a matching de-identification
assessment; publication requires a matching model review. The assessment
issuer is represented but must be authenticated by the Host.

The checked cases reject another source, changed dataset bytes, a different
deployment target, expired or revised grants, missing or wrong-kind
assessments, and changed model bytes. Clinical inference separately requires
an exact patient binding, current clinical validation, and audit readiness.
A source withdrawal makes future training, publication, and endpoint use of
the joint branch deny; it leaves the hospital A branch available. The
resource's lineage revision and the selected catalog revision must match.

The catalog is derivation evidence, not a replacement authorization system.
Cedar evaluates the policies produced by LeanPOO. The same requests are also
[[file:ReplayExport.lean][exported]] and replayed against the official Cedar
Rust runtime by =just example health model-stewardship=. The Host must authenticate
every source edge, assessment issuer and result, approval, patient binding,
model bytes, destination, clock, and catalog revision. At effect time it must
atomically compare the actual effect and current state with the admitted
operation. The typed assessment and grant values are synthetic Host claims;
neither Lean nor Cedar verifies external signatures, reads actual data, runs a
training job, publishes a model, or durably records an audit. Withdrawal does
not delete an already trained model or undo a previously served inference.
Quarantine, review, retirement, and any retraining are separate real-world
operations requiring their own evidence.

* Public sources and interpretation

- [[https://news.microsoft.com/source/2026/06/02/mayo-clinic-and-microsoft-collaborate-to-develop-a-frontier-ai-model-for-healthcare/][Mayo Clinic and Microsoft, June 2026]] announce development of a
  Mayo-owned healthcare foundation model using de-identified clinical and
  longitudinal data, with initial use in Mayo's clinical environment and a
  planned Azure Foundry API. The announcement does not document this example's
  approval flow or establish that the planned API is already deployed.
- [[https://www.hhs.gov/hipaa/for-professionals/special-topics/de-identification/index.html][HHS de-identification guidance]] describes two recognized methods and
  residual re-identification risk. Its HIPAA boundary must not be mistaken for
  proof of technical safety or for every institution's research governance.
- [[https://www.hhs.gov/ohrp/sachrp-committee/recommendations/irb-considerations-use-artificial-intelligence-human-subjects-research/index.html][HHS human-subjects research recommendations]] discuss oversight and
  consent challenges when AI uses clinical records collected for care.
- [[https://www.nist.gov/programs-projects/hl7-ai-transparency-fast-healthcare-interoperability-resources-fhir][NIST on AI Transparency on FHIR]] describes proposed AI involvement tags
  and richer Provenance records. That guide represents provenance; it does not
  verify whether a claim is true or assess model quality.
- [[https://proceedings.mlr.press/v297/lee26a.html][FHIR-AgentBench (2026)]] reports retrieval and reasoning difficulty over
  realistic FHIR questions. This scenario checks authorization and lineage,
  not correctness of an AI answer.

All identifiers and decisions here are synthetic. The example is motivated by
the public collaboration and research problems, not a reconstruction of Mayo
Clinic or Microsoft's internal design. It contains no patient data, model,
weights, training service, FHIR parser, or provider-specific API call.
