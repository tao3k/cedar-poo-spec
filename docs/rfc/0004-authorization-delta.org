#+TITLE: RFC 0004: Authorization Delta over Cedar Policy Revisions
#+OPTIONS: toc:nil

* Contract

[[file:../../CedarPooSpec/AuthorizationDelta.lean][AuthorizationDelta]] asks whether
a C4-composed Cedar policy revision grants any request that its predecessor
denied. It uses =Cedar.SymCC.implies? after before=; Cedar owns the symbolic
compiler, verification condition, and authorization semantics. This adapter
owns revision compilation, query coverage, provenance, and result admission.

For each request type declared by the supplied schema, the queried property
is:

#+begin_example
Allow(after, request, entities) -> Allow(before, request, entities)
#+end_example

The analysis checks that the schema is well formed and both policy sets pass
Cedar validation. It calls Cedar's =wellTypedPolicies= in every schema type
environment, then constructs =SymEnv.ofTypeEnv=. It rejects an empty list of
environments rather than reporting a vacuous no-expansion result. A solver
error or unknown result is an error, never a no-expansion result.

An expansion result carries a concrete Cedar request and entity store. The
adapter replays the original, untransformed policies and requires =Deny=
before and =Allow= after. It also reports which policy IDs changed according
to the C4 revision. The no-expansion result is scoped to the request types,
entities, and context values represented by the schema environments. It is
not a claim about inputs that violate the schema or host-supplied facts that
are false.

The upstream [[https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/README.md][Cedar Lean README]] identifies the definitional symbolic compiler,
its implication and equivalence queries, and the soundness and completeness
theorems. SPEC calls those public Cedar APIs instead of implementing another
authorization semantics.

* Evidence and trust boundary

Cedar's [[https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/Cedar/Thm/Verification.lean][verification theorems]] establish the meaning of symbolic implication
under their well-formedness premises. This repository does not duplicate the
symbolic compiler or prove an independent authorization semantics. CVC5 is an
external solver: an unsatisfiable answer is used as analysis evidence, while
the concrete counterexample is replayed by Cedar Lean and by the official
Rust =cedar-policy= authorizer. The result is a checked analysis report, not
a kernel proof of the solver's answer.

[[file:../../CedarPooSpec/AuthorizationDeltaProof.lean][AuthorizationDeltaProof]]
connects one POO revision to Cedar's =verifyImplies_is_ok_and_sound= theorem.
Its conclusion applies to the original before and after policy sets, under
the theorem's well-formedness premises, if Lean receives a proof that the
generated assertions are unsatisfiable. The current external solver does not
produce such a Lean proof. The executable report and the theorem therefore
remain distinct evidence types.

The [[file:../../Examples/Governance/AuthorizationDelta.lean][ticket-sharing
case]] checks two revisions from the same POO graph. A device-posture overlay
does not expand Allow within the schema. A later ticket grant produces a
counterexample with =User::"alice"= reading =Ticket::"ticket-b"=: the old
revision denies and the new revision allows. The generated Rust manifest
replays both responses, their reason IDs, and their error IDs through the
official Cedar authorizer.

The [[file:../../Examples/Enterprise/Agent/Payment/AuthorizationDelta.lean][finance-agent payment case]] checks an emergency account freeze and its
removal over four schema request types. The freeze has no new Allow; removing
it produces a payment authorization witness that is also replayed in Rust.

* Decision delta versus executable delta

Cedar's [[https://docs.cedarpolicy.com/auth/authorization.html][authorization algorithm]] skips a policy that errors and reports its ID in
diagnostics. A Host in this repository executes only an error-free Allow.
Consequently, equal Cedar Allow/Deny decisions need not mean equal Host
execution decisions. The [[https://github.com/cedar-policy/cedar/issues/2428][Cedar issue on an erroring AI-agent governance forbid]] shows a
concrete version of this hazard in a schemaless deployment; this library
requires a schema and validation, which rejects that issue's type mismatch.
Schema validation still permits runtime arithmetic, extension, or missing
entity errors, as the [[https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/README.md][Cedar Lean documentation]] states.

[[file:../../CedarPooSpec/AuthorizationDeltaOperational.lean][AuthorizationDeltaOperational]] is a separate, conservative qualification for
Hosts with the error-free rule. It invokes Cedar's public =neverErrors?= query
for every baseline policy and every changed or newly introduced policy, in
every schema environment. An error witness is replayed against the original
policy, with request and entities validated; solver errors fail the query.
Only after all these checks pass does it run the existing two-direction
authorization delta. Identical policy bodies on the two sides reuse the same
error check within each environment. The reported check count exposes this
cost; the external solver's unsatisfiable answers remain analysis evidence,
not Lean kernel proofs.

The [[file:../../Tests/Governance/AuthorizationDeltaOperational.lean][governance regression]] adds a POO forbid that can overflow at the minimum
integer value. Its condition is false on non-erroring inputs, so Cedar's
decision delta is =equivalent-in-schema=. On the error witness, both Cedar
responses are =Allow=, while the revised response has an erroring policy;
the Host's executable decision therefore changes. The operational query
returns that policy and witness instead of issuing an equivalence report.
The same witness is replayed against both POO revisions by the official
Rust Cedar authorizer, including expected error-policy IDs. This regression
is maintained under =just check-authorization-delta-operational=.

This qualification is intentionally stricter than the exact proposition
=error-free-Allow(after) -> error-free-Allow(before)=: it refuses any policy
that might error anywhere in a covered schema environment, including requests
both revisions deny. A future exact query should extend Cedar's verified
symbolic semantics or use an upstream-supported predicate over diagnostics;
it must not silently treat plain =implies?= as that query.

* Revision explanation and proof reuse

[[file:../../CedarPooSpec/AuthorizationDeltaEvidence.lean][AuthorizationDeltaEvidence]]
attaches the POO compilation to the symbolic result. For each changed policy
body it records the before and after owner, the ordered =extend=, =overlay=,
and =remove= history, and the roots that may need recompilation through C4's
reverse dependency graph. It also reports the exact policy bodies needing new
validation, the unchanged bodies eligible for certificate reuse under the
same schema, and the authorization proof object's changed dependency key.

These are distinct forms of evidence. A symbolic witness establishes a
before/after behavior difference for the covered schema. The edit history
shows which POO objects produced the two policy sets; when several policies
change, it does not prove that any one edit alone caused the witness.
=potentially_invalidated_roots= is a compilation footprint, not a list of
requests whose decisions changed. Reuse of an old validation certificate
requires the validated baseline and unchanged schema as stated in
[[file:../../CedarPooSpec/Revision.lean][Revision]]; the JSON report alone is
not a certificate.

The ticket-sharing gate now queries both directions. Its device-posture
overlay has no authorization gain but has a loss witness; its later =extend=
has a gain witness and no loss. The official Cedar Rust authorizer replays
both witness pairs. This demonstrates why text or policy-ID diff alone does
not answer which requests changed.

* Determining-policy delta

Cedar returns the IDs of the policies determining its decision. An =Allow=
may remain =Allow= after a POO removal while a different owner now supplies
the remaining grant. That changes audit explanation and responsibility even
when the decision sets are equivalent. [[file:../../CedarPooSpec/AuthorizationDeltaReasons.lean][AuthorizationDeltaReasons]] uses the upstream
[[https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/Cedar/SymCC.lean][=matchesEquivalent?= and =neverMatches?= queries]] to inspect each changed policy
ID over every schema environment. It first qualifies both policy sets with
the error-free operational check. A matching difference becomes a reason
witness only when original Cedar responses actually have different
=determiningPolicies=. The report carries C4 edit owners, proof footprint,
and potentially invalidated roots as candidate provenance; it does not
assign sole causality when multiple edits are present.

The outcome has three useful cases. A concrete changed reason is replayed by
the official Rust Cedar authorizer. If the decision is equivalent in the
covered schema and every changed ID retains its effect and matching behavior,
=reasonStable= is true, subject to external solver evidence. A masked match
can also be discharged when every version of a changed permit is covered by
one identical forbid in both revisions. The adapter checks this with Cedar's
verified =matchesImplies?= query in every schema environment. The
[[file:../../CedarPooSpec/AuthorizationDeltaEffectiveReasonsProof.lean][dominated-permit theorem]] proves the concrete rule: a permit covered by a
matching forbid cannot occur in the final determining set. The report lists
these discharged IDs and counts the added implication queries. A mask without
such a certificate, or an effect change, remains unresolved; one masked
witness alone cannot establish universal reason stability. The
[[file:../../Tests/Governance/AuthorizationDeltaReasons.lean][governance regression]] exercises an actual reason change and a dominated
permit removal whose final reasons remain stable.

There is a fourth, separate change surface: ownership can move while the
Cedar policy body, ID, decision, and determining-policy IDs remain identical.
An overlay of the same body under another C4 module changes who is responsible
for that policy, without requiring a new Cedar validation certificate or
authorization proof dependency. =Revision.provenanceChanges= compares compiled
owners and applied edit trails independently of =changedPolicyIds=;
=provenanceStable= is therefore reported separately from =reasonStable=.
The governance regression transfers an unchanged ticket grant to a new owner
and requires an empty policy-body delta together with a nonempty provenance
delta. This keeps accountability review from mistaking Cedar behavioral
equivalence for unchanged stewardship. Cedar's
[[https://docs.cedarpolicy.com/policies/syntax-policy.html][policy syntax documentation]] says annotations are stored for applications
but are not processed by Cedar; this POO owner trail is likewise application
governance metadata, not a new Cedar authorization rule.

** Effective reason equivalence

The upstream-query route above resolves a common forbid-dominated permit,
but can still leave other masks unresolved. The
[[file:../../CedarPooSpec/AuthorizationDeltaEffectiveReasons.lean][effective-reason analyzer]] asks a more precise question for every policy ID
in the union of the two revisions. Cedar's
[[https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/Cedar/Thm/Authorization.lean][=determiningPolicies_of= theorem]] says that final reasons are the satisfied
permits on =Allow= or the satisfied forbids on =Deny=. For each ID, the
analyzer constructs an analysis-only policy set whose =Allow= decision is
equivalent to that ID's membership in the original final reasons:

#+begin_example
absent ID  -> empty policy set
permit ID  -> all original forbids + that permit
forbid ID  -> that forbid's condition as a permit
#+end_example

It then calls Cedar's upstream =equivalent?= query on the two analysis policy
sets. The [[file:../../CedarPooSpec/AuthorizationDeltaEffectiveReasonsProof.lean][Lean reduction theorem]] proves for every concrete request and entity
set that the analysis =Allow= decision equals final reason membership, under
unique policy IDs. The query applies the same entity-hierarchy constraints
as upstream equivalence checks and replays every counterexample
against the original Cedar policy sets. The analyzer first applies the
error-free operational qualification. Both public reason analyzers reject
duplicate policy IDs before selecting an ID for symbolic evaluation; the
POO compiler produces unique IDs, but callers can also construct a =Revision=
directly. A solver failure or a model that fails
the original Cedar replay is an error, never a stable result. Identical Cedar
policy lists skip the reason queries while still reporting POO provenance.

The proof module also proves that a unique policy ID is in Cedar's final
determining set exactly when that policy matches and its effect agrees with
the final decision. The same module proves that every final determining ID came from
the compiled policy list, which justifies querying the union of the two
revisions' IDs. The focused regression also rejects a manually constructed revision
with duplicate IDs before any solver query.

The [[file:../../Tests/Governance/AuthorizationDeltaEffectiveReasons.lean][focused regression]] distinguishes four cases: removal of one of two
independent grants changes final reasons but not the decision; an always
matching incident veto masks that removal for every input in the schema;
moving the unchanged policy to another POO owner changes provenance only;
and flipping a permit to a forbid removes the other permit from the final
reason set. Concrete reason witnesses are replayed in Rust Cedar.

The reduction is proved in Lean and uses Cedar's existing verified
authorization-equivalence analysis rather than a new SMT encoding. As with
the upstream query, the external solver and schema-environment coverage are
trust boundaries: =solverReasonStable= means no difference was found by those
queries in the checked environments. Concrete witnesses are additionally
replayed against the original Cedar policy sets. The conservative analyzer
remains useful when callers want sufficient conditions based on
=matchesEquivalent?= and =neverMatches?= without constructing per-ID policy
sets.

* API and check

=analyze revision schema= returns a report or a typed error. =analyzeModel=
first compiles two named POO roots. The report contains the changed policy
IDs, the number of schema environments checked, and any expansion witnesses.
Applications decide whether an expansion is authorized; the library exposes
the change without making that governance decision.

=analyzeImpact= and =analyzeModelImpact= query both directions. =gains=
contains requests denied before and allowed after; =losses= contains requests
allowed before and denied after. Both directions validate the policies, check
every schema environment, and replay each witness against the original Cedar
policy sets. A completed report classifies the covered behavior as
=equivalent-in-schema=, =gain-only=, =loss-only=, or =mixed=. A
provider-independent healthcare [[file:../../Examples/Health/Pseudonymization/AuthorizationImpact.lean][impact example]] checks that a POO
incident overlay only removes access and that withdrawing the overlay only
restores access.
=analyzeModelExplained= and =analyzeModelImpactExplained= keep those Cedar
queries and add the C4 revision and proof footprint to the returned result.

=compareOperationSnapshots= addresses a different kind of change: one
principal/action/resource under two concrete Host-supplied request and entity
snapshots. It validates both snapshots and policy sets, rejects Cedar policy
evaluation errors, and returns the two decisions. This is finite evidence for
the selected operation, not a universal symbolic result. The healthcare
example uses it to observe an approval withdrawal while the policy root stays
the same, and to compare scope, token-key, and transformation revisions of a
target dataset. Neither analysis authenticates a Host fact or commits an effect.

[[file:../../CedarPooSpec/AuthorizationDeltaCompound.lean][AuthorizationDeltaCompound]]
extends the finite comparison to an ordered set of required Cedar checks.
The two sides must contain the same requests in the same order, although
their POO roots and authenticated entity snapshots may differ. It reports
each layer and the conjunction that governs the complete operation. The
[[file:../../Examples/Enterprise/Agent/Chain/README.org][agent-chain case]] demonstrates a local gain masked by an incident veto.
This does not replace symbolic analysis of individual policies, and does
not establish delegated authority or temporal budget safety for arbitrary
agent histories.

[[file:../../CedarPooSpec/AuthorizationDeltaInteraction.lean][AuthorizationDeltaInteraction]] compares a base, two independent POO
branches, and their combined root under one Cedar schema. If neither branch
adds an Allow but the combined root does, it reports a joint-only gain and
replays the same witness on both branches. It rejects a proposed interaction
unless both branches inherit the base and the combined root directly mixes
those branches. Its first use is the
[[file:../../Examples/Enterprise/Agent/Payment/README.org][AI-agent payment joint-release case]]. Branch reports retain C4 edit owners
and proof footprints. When either branch already gains access, the analyzer
returns =branchExpanded= rather than claiming to have exhaustively classified
joint effects. It checks Cedar decisions; Host execution still needs the
error-free and transaction gates.

[[file:../../CedarPooSpec/AuthorizationDeltaRelease.lean][AuthorizationDeltaRelease]] captures a four-root analysis with the exact
compiled policies, schema representation, C4 ancestor modules, and a
Host-supplied epoch. Its freshness check rejects changes to any reviewed
dimension while allowing unrelated owner additions. The no-gain candidate
API refuses joint gains until a separate approval has occurred. It does not
authenticate that approval, read a provider's active policy version, publish
policies, or make the comparison and effect atomic; those remain Host duties.
Its pure =advanceNoGain= transition compares the active root, exact active
policy set, and epoch with the reviewed base. It also requires the Host's
execution mode to be enforcing. It returns the composed policies with the next
version and rejects a second use of the same review after a successful
transition. The Host must obtain the actual active policy set and execution
mode from the deployment boundary rather than trusting a caller's copy.
This is a material distinction: [[https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-enforcement-modes.html][AgentCore's enforcement-mode documentation]] says
=LOG_ONLY= evaluates policies without blocking tool calls, and disabling the
gateway policy engine bypasses those checks. This generic SPEC state models
the distinction without importing an AWS-specific API.

Even an enforcing policy version is a snapshot property. The 2026
[[https://arxiv.org/abs/2609.15803][delegated-authorization study on sequential control]] analyzes safety over
state transitions, where one agent action changes later feasible actions.
Its results do not certify this release API: the current delta quantifies
over Cedar requests in one schema environment and the pure release transition
does not model future agent histories. An application requiring trajectory
safety must add an explicit state-transition model and Host effect receipts.

The repository devenv provides cvc5 and sets =CVC5= to its absolute executable
path. After activating the repository through =direnv=, run the gate through
the cached profile entrypoint:

#+begin_src sh
./.devenv/devenv-profile-exec just check-authorization-delta
#+end_src

The recipe limits Lean time and memory, checks both expected outcomes, and
replays the witness through Rust Cedar. =just check= includes this gate. CI
downloads CVC5 1.4.0, checks its SHA-256 digest, and runs the same checks.
No solver binary is committed.
The operational gate also runs under =just check-delta= and CI. It uses a
separate Lean test module so the ordinary Cedar decision contract stays
unchanged. Cedar [[https://github.com/cedar-policy/cedar-spec/issues/634][issue #634]] documents the cost of querying every environment in a
large schema; this qualification adds error queries, so production use should
measure environment counts and cache exact policy/schema results before
claiming interactive latency.
The reason gate is =just check-authorization-delta-reasons= and runs under
=just check-delta= and CI with the same solver and official Rust replay.
The effective-reason analysis has a separate
=just check-authorization-delta-effective-reasons= gate, also included in
=just check-delta= and CI.
The four-root payment interaction uses =just check-payment-interaction= and
replays all four responses through the official Rust authorizer.
The payment case has its own =just check-payment-delta= gate.
The healthcare impact case has =just check-health-authorization-impact=; it
replays the incident, recovery, approval-withdrawal, and dataset-lineage decisions through the
official Rust Cedar authorizer. =just check-delta= and CI include it.

* Scope

Authorization Delta is a family of claims with different quantifiers and
evidence. They must remain separate in release decisions:

| Change surface | Current evidence | Exact limit |
|----------------+------------------+-------------|
| Policy bodies under one schema | Symbolic gains/losses and concrete Cedar replay | The same schema and its represented request/entity environments. |
| Error-free Host admission | =neverErrors?= qualification before symbolic gains/losses | Conservatively rejects any possible policy error, including on denied requests. |
| Determining-policy change with unchanged decision | Conservative upstream matching queries and concrete Cedar reason witnesses | The sufficient-condition analyzer may leave non-dominated masks unresolved; use effective-reason equivalence for the broader query. |
| Effective final-reason membership | Lean-proved reduction to Cedar's authorization equivalence, with concrete Cedar replay | External solver answers and schema-environment coverage remain trust boundaries. |
| Two-branch POO composition | Three Cedar gain queries, C4 provenance, and a four-root replayed witness | Joint-only classification requires both branches to have no gain; other interactions remain unclassified. |
| Release-review freshness | Four compiled policy sets, relevant C4 modules, exact schema representation, and Host epoch | Pure compare only; Host authenticates approval and makes publication atomic. |
| Enforcement configuration | Pure release transition rejects observing or disabled Host mode | Host must read actual deployed mode and bind it atomically to publication; Cedar implication alone cannot certify this. |
| POO owner or edit-trail transfer with unchanged Cedar behavior | Compiled owner and edit-trail comparison | Governance provenance only; it does not assert a changed authorization decision or reason ID. |
| Approval, classification, or other entity/context facts | Two validated concrete snapshots | One operation and two Host-supplied snapshots; no future-state quantifier. |
| Required multi-hop checks | Ordered compound snapshot comparison | A fixed chain topology; delegation and future history remain external. |
| C4 edit ownership and proof reuse | Compiled owner/edit trail and dependency footprint | Potential invalidation, not proof that one edit caused a witness. |
| Schema evolution and operation history | No unified delta query | Revalidate, reproject, and analyze with an explicit migration relation before any cross-schema claim. |

For release review, policy-body changes still require explicit Cedar queries.
=changed_policy_ids= alone cannot establish a behavior change: edits can be
masked by another permit or veto, and two policy sets may authorize the same
requests for different reasons. A four-root composition requires comparison
with the final mixed root even when each branch was separately reviewed.

The recently proposed [[https://arxiv.org/abs/2609.31039][MetaPermit]] moves some tool-call meaning into LLM-inferred
meta-attributes. That is a useful contrast: even if Cedar policy bodies stay
fixed, a changed inference result changes the Host-supplied snapshot and may
change admission. The model inference is evidence that the Host must bind and
audit, not a POO policy revision. This paper's evaluation does not validate
this SPEC's Delta implementation or its Host transaction.

This feature does not authenticate identity, entity facts, or context values;
those are supplied by the host. It does not make authorization and effect
commit atomic. The ordinary delta analyzes Cedar's Allow/Deny decision; the
optional operational qualification checks a sufficient condition for the
application's error-free execution rule. Neither covers policy changes under
a different schema, unvalidated host facts, or future operation histories.
Those boundaries remain explicit at the deployment interface.
