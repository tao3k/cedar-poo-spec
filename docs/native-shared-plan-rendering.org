* Original construction carries the resolver

Previously =Object.compile= discarded the resolver table after extracting the
root order. Cedar's later preparation seeded only that root result and rebuilt
internal ancestor metadata. =Object.Schema.preparation= now retains the actual
immutable-graph-indexed preparation before original compilation. =Object.compile=
uses that field, and the returned Plan retains the same Schema. Source-current
Cedar =Model.prepareC4= directly obtains the field, including resolved ancestors.
Active staged schemas share it too; raw or stale models prepare independently.

This is ownership of the existing resolver, not a result cache keyed by names.
=Object.compile_precedence= proves original complete precedence/error equality;
=Object.compilePrepared_eq= still equates entire Plan results. Cedar's universal
=Model.prepareC4_current= proves actual owner equality (with the necessary graph
transport). All new proofs use only the original three standard Lean axioms.
Validation, original error order, checked-mode refusal fallback and source
identity controls remain. Original 42 result replays and 80 reordered/fallback
replays pass, now also exercising the ordinary object compiler.

Declaration-only revision proves preservation of the actual preparation field.
Graph edits must create a fresh indexed owner; production graph transformers and
four SharedFamily negative fixtures now do so without changing their assertions.
A stale graph's preparation is rejected by the type checker. The native addNode
closure captures declaration and graph data, releases the old preparation and
creates the new graph's thunk; it does not retain a chain of old resolver tables.

Generated C verifies both sides: original =Object.compile= reads Schema field 2
and forces its existing thunk; Cedar's source-current branch reads that same
field without calling =C4.prepare=. Only the raw/stale branch constructs a new
preparation. This closes the first duplicated table for original owned objects.
The existing whole-graph first-demand cost remains for independently prepared
single-root graphs; no universal complexity or constant-cost claim is made.

* Before-main investigation and its limits

Earlier owned-PID sampling located stationary raw CPU/fault/page-in counters and
entry frames at =_dyld_start + 0=. This round used Apple's installed System Trace
on one exact prior native image to investigate the kernel boundary. The target
started, but packaging exceeded the fixed 30-second tool ceiling. Export reports
Document Missing Template Error. The partial raw trace and incomplete child
output are retained as failed evidence; neither is accepted as a native run.

A narrow read-only system-log query for that exact PID/path succeeds. Kernel
AMFI/CoreTrust messages name the same image; a source-bound syspolicyd request
precedes main. Following its exact TCC request ID identifies
=kTCCServiceDeveloperTool=, =preflight=yes=, not a proven business-file permission
failure. This instrumented launch can induce developer-tool checks. Those events
prove the observed assessment path, not an exclusive ordinary-startup cause or
callback duration. The [[https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_exec.c][Apple XNU exec source]] documents signature/launch upcalls, but source alone does
not identify which installed-kernel callback consumed a measured interval.

Actual first-file pre-main spans are 1335.366/1162.383 ms in the reference and
1339.434/1160.782 ms in the candidate, versus repeated medians 39.729/39.632 ms.
The long tail is not removed by this algorithm change.

Four exact fresh-file PID/path/time-window queries from the completed normal
phase cohorts return successfully with no matching log events. Absence of stored
messages does not prove absence of assessment. No native workload was rerun to
obtain favorable traces. A read-only off-CPU DTrace capability check requires an
administrator password; that capture was not available. Signing, quarantine,
SIP, logging configuration and security settings were not changed.

The precise ordinary pre-main kernel/service wait therefore remains unresolved.
Supported owned-PID kernel/off-CPU evidence is needed to close it; neither C4
work nor a specific security callback is assigned the entire delay by inference.
