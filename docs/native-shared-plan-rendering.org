* SDK first parsing consumes the existing complete wire

Schema preparation now passes its source-owned complete JSON encoding to public
=Schema::from_json_str= rather than cloning the JSON tree solely to transfer
ownership to the SDK. EntitySourceJson likewise extends its existing immutable
owner with one lazy full encoding. Source-table uniqueness and SDK parsing borrow
that same encoding. =EntitySlot= still has one schema-bound prepared slot and
retains the original lazy parse point, source comparison and replacement rules.
There is no global prepared-Entities cache or schema/request admission cache.

Both SDK string entrypoints deserialize directly into their typed SDK input,
then execute the same SDK semantic preparation. Source wire is the encoding of
the already normalized immutable Value, not an unchecked original substring or
a producer-supplied authority. Source equality, receipt hashes and public wire
shape remain unchanged. The source owner stays live through its existing catalog
lifetime and releases its encoding with that owner.

On string-route rejection, the original Value-consuming SDK route supplies the
exact original error. =schema_diagnostic_reparses= and =entity_diagnostic_reparses=
explicitly record this additional work; logical source preparation counters
retain their meaning. The actual-catalog native benchmark requires BOTH new
counters to be zero, as well as all previous parse/reuse/authorization counts.
Rejected inputs may execute two SDK parses; this is not hidden as one physical
parse or asserted as a failure-path speedup.

The test-only uncached Entities oracle still uses the original Value route.
All catalog replays compare against independent authoring manifests and original
SDK preparation. Added controls cover exact schema/entity rejection strings,
valid/invalid/Unicode schemas, unchanged slot after failure, shared encoding,
public serialization and equality independent of memo state. Core passes 9 tests;
Runtime passes 56 with one pre-existing ignored test, which the full gate also
executes explicitly. SDK equivalence here is executable differential evidence;
Lean proofs continue to establish their typed object/source/Contract laws.

Walls above sum the two native child lifetimes; external observation-launch

identify an exclusive scheduler, competing task or OS assessment mechanism.

* Copy versus same-inode/new-path pre-main diagnosis

A separate 24-child diagnostic uses the existing launcher, the real Lean catalog
and Rust launch_probe CLI, opt-in thread states and read-only dyld logging.
Each runtime has two copy cohorts and two hardlink cohorts, three trials each.
Hardlinks are verified to share exactly one device/inode with the source image;
copy cohorts have two distinct inodes. Every image hash, complete stdout, clock,
stderr byte range and stopped observer validates. One near-exit task-info read
is unavailable and retained; there are no thread-read errors or truncations.

| Instrumented entrypoint | First start in each path, pre-main ms | Initial waiting span ms |
|-------------------------+---------------------------------------+-------------------------|
| Lean copies | 1139.413 / 1147.212 | 1071.194 / 1082.219 |
| Lean same-inode hardlinks | 810.536 / 763.306 | 723.761 / 690.172 |
| Rust copies | 2886.531 / 1412.788 | 2878.304 / 1391.738 |
| Rust same-inode hardlinks | 4045.528 / 4.272 | 4035.332 / no sampled initial plateau |

Repeated same-path starts have no sampled initial plateau in these cohorts.
Both Lean hardlink paths still wait, despite sharing the same inode and image.
Rust's second hardlink path does not exhibit the same plateau. This contradicts
a simple inode-only first-execution explanation; it does not establish a universal
path-only, runtime-only or assessment cause. Birth/change timestamps and other
file metadata also differ across materializations. Extended-attribute reading
is unavailable in this observer and remains explicitly recorded.

Initial samples show one waiting handle with stationary task CPU, faults,
page-ins, context switches and resident bytes, before first observed owned loader
activity. Arrivals are upper bounds, not child write times or exact loader entry.
Samples do not prove continuous state; public handles are not unique thread IDs.
Eight exact owned-PID/path/time-window OS queries return zero events, not proof
that no assessment occurred. Precise kernel wait event/service remains unresolved.
The earlier noninteractive off-CPU capability check needs administrative access;
no signing, SIP, security or logging configuration is changed.

* Remaining whole-stage priorities

P0: obtain qualified kernel off-CPU evidence for the pre-loader waiting interval
when an administratively equipped environment is available. Preserve the new
same-inode counterexample; do not assume inode caching alone resolves startup.

P1: use the executable POO API/caller map for future source revisions. Remaining
SDK semantic/type preparation and independent validation must be distinguished
from JSON transfer cost. Optimize within the same source/graph owners and public
SDK interfaces, with source-bound analytic laws and full differential replay;
do not add an index merely because a reference-model definition has that name.

P2: require complete native process/resource gains before declaring the latency
objective achieved. The current implementation reduces allocation work but has
not met stable whole-entry speedup or peak-memory improvement. Keep all source,
Contract, proof, admission, ordinary-process, cold and rejected-control boundaries
for the next algorithmic candidate.
