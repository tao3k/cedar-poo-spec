* Algorithm and representation changes

** Schema source ownership crosses the whole boundary

SchemaSourceJson previously cloned its owned JSON value. Source-table planning,
manifest resolution and PreparedSchema each copied that tree; planning and
acquisition repeatedly serialized it for full-source lookup keys. It now shares
a private immutable JSON source record through Arc, matching the existing policy
source ownership. The record memoizes its complete JSON identity once. Schema
source table, finite-use plan, typed ValidatedManifest and PreparedSchema carry
that same owner, rather than materializing another untyped JSON source.

Planning counts borrowed complete identities while source owners remain alive;
only shared keys enter the finite retained plan. Acquisition borrows the memoized
key. SDK state still retires on its last planned use, and validation and request
preparation still execute per invocation. No schema digest, source-table index,
revision name or observed decision substitutes for complete source identity.

The public schema field is now the named immutable SchemaSourceJson boundary.
There is no public dynamic-Value constructor or mutable dereference. Editing
creates a new source through normal typed deserialization. Existing Host and all
runtime consumers use this boundary directly; there is no compatibility wrapper
or parallel manifest. The SDK's public Value-consuming first-parse boundary still
needs its own owned input; this stage does not bypass SDK schema parsing.

** Entities and source-table checks

EntitySlot uses the existing exact JsonSourceIdentity comparison. Pointer equality
handles the same immutable owner without traversing its JSON; independent owners
still compare complete content, including floating-point signed zero. The
schema-bound one-slot lifetime, lazy parse point, failure behavior and receipt
hashing remain unchanged. There is no catalog-wide prepared-Entities cache.

Source-table uniqueness checking now processes each source kind in turn. Policy
and schema keys are borrowed from their actual source owners. The checker no
longer builds simultaneous vectors of cloned full encodings for all three kinds.
Complete identities and kind separation remain authoritative. Entity source
encoding remains required for independent table entries.

* Rust pre-main waiting: new independent evidence

A separate fixed six-child cohort runs the existing Rust launch_probe example
through the real full-catalog CLI, with the existing thread-state observer and
read-only dyld loader logging. It is a diagnostic entrypoint, not the ordinary
bridge binary or ordinary latency evidence. All six complete replay outputs
match their golden, clocks are valid, stderr bytes are accounted and observers
stop. All thread reads succeed without truncation; three near-exit task-info
reads are unavailable and remain recorded.

Two fresh-file children have pre-main 556.945 / 468.010 ms. Their initial sampled
waiting plateaus span 530.765 / 420.581 ms across 78 / 60 samples, with stationary
task CPU, faults, page-ins, context switches and resident bytes. Readers are ready
at 11.574 / 31.885 ms; first owned loader lines arrive at 547.455 / 457.160 ms.
Four repeated starts have pre-main 28.089 / 14.515 / 19.129 / 17.195 ms, with no
sampled initial waiting plateau. This extends the preceding Lean evidence with a
Rust entrypoint; it does not prove a universal runtime-independent cause.

Arrival timestamps are upper bounds, not child writes or exact loader entry.
Samples do not establish continuous state; handles are not unique thread IDs.
Exact owned-PID/path/time-window system log queries return zero events, not
proof of no assessment. The specific kernel wait event/service remains unknown.
The prior noninteractive off-CPU capability check requires an administrative
password. No signing, SIP, security or logging configuration is changed.
