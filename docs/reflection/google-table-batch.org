#+TITLE: Reflection: Google Table Batch and LeanPoo
#+OPTIONS: toc:nil

* LeanPoo fit for this iteration

The table recipe's token profile is already a declared, typed selection. A
batch repeats one recipe over ordered rows and sums a bounded byte cost. The
wire check binds one response shape to that already selected order.
These rows do not contribute independent method definitions, inherited
slots or a reusable dependency graph. A LeanPoo object per row would add
construction and lookup without strengthening ordinal, byte, or complete
response checks. The existing LeanPoo protection profile is used in the
storage branch; this independent Google branch uses a simple pure fold.

* Executable evidence and boundary

[[file:../../Tests/Pseudonymization/TableBatch.lean][The Lean test]] and
[[file:../../Tests/Conformance/google-table-batch-v1.json][checked fixture]]
fix two accepted and eleven denied selection cases, plus two accepted and
ten denied wire response cases, including swapped equal-context rows. Rust
replays the exact fixture, then its
Cloud batch planner rechecks current per-row authorization and actual Arrow
cells before the bridge forms one request. The bridge structurally checks a
Host-supplied response and verifies a generated marker for every row; neither
pure fold authenticates its origin, reverses
external partial work, or joins separate policy claims into one grant.

* Reconsideration trigger

If table recipes acquire independently owned, inherited transformations,
compose those owners through LeanPoo and retain the explicit ordered row and
current claim checks at the physical boundary.
